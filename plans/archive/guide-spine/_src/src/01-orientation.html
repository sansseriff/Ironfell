1.1The one idea

Before September 18, the scene lived inside Bevy. Now it lives in a document, and Bevy displays it.

Before the change, each demo object was its own Bevy thing. The draggable square was a Bevy resource called DraggableSquare holding a position. The field of small squares was a set of MiniSquare components. The torus was spawned by hand in setup_3d_scene. The timeline's state was a resource called TimelineState. The Svelte inspector could reach into Bevy and overwrite any component directly. Nothing recorded what changed, so there was no undo, no file format, and nothing a language model could read or safely edit.

The new design puts one object at the centre: a document (the Store in the new iron_document crate). It holds every authored fact about the scene. Everything that wants to change the scene submits an operation to it: a drag, the undo key, a loaded file, a model's edit. A separate piece of code, the reconciler, reads what changed and updates Bevy's entities to match.

An analogy from the shell code you already work in: in Svelte, a $state variable is the truth and the DOM is derived from it. You never edit a DOM node by hand and expect the change to stick, because the next update would overwrite it. The new architecture treats Bevy the way Svelte treats the DOM:

The vision documents make the same comparison with other tools: Blender's scene data vs its evaluated depsgraph, or USD's stage vs Hydra. The name “spine” comes from plans/document-spine.md, the design record the model wrote before coding and then kept updated as each step landed. That file is still the best one-page statement of the decisions. This guide explains the code that implements them.

1.3Where everything lives

The app runs in two places. The main thread runs the Svelte shell. A web worker runs one wasm module that contains Bevy, the renderer, the bridge and the document store. The TypeScript model surface also runs in the worker, so its calls into the store are ordinary function calls, not messages.

1.4One drag, end to end

Here is a single interaction followed through every system: you drag the dark square (node #M in the demo scene) and then press Cmd+Z. Don't try to understand each step yet. The point is to see that there is one path, and to recognise these names when later parts cover them properly.

  1. Pointer down. The main thread posts leftBtDown; worker.ts calls left_bt_down, which hands Bevy a mouse event.
  2. Hit test. pick_document_2d_system maps the cursor into each 2D node's own coordinate space and finds the square.
  3. Drag starts. interaction_decide_system begins a 2D drag. It first asks the store whether x or y are bound or animated, because those axes may not move.
  4. Every frame while dragging. drag_apply_system moves the entity's Transform so the square follows the pointer. The document is not touched. This is the “optimistic” half.
  5. Release. drag_commit_system compares where the entity ended up with what the document says and queues one transaction, "move rect", containing Set ops for transform2d.x and transform2d.y.
  6. Next frame: apply. sync_document passes it to Store::apply. That works on a copy of the document, runs set for each op (which records the old value as the inverse), and commits the copy only if every op succeeded.
  7. Reconcile. The sync reads the new transaction off the history log, collects the node ids it touched, and calls reconcile, which rewrites the square's Transform from the document. It gets the same value the drag left, so nothing visibly moves. It then tells the shell the version changed, and the Document panel re-reads its view.
  8. Undo. Cmd+Z is caught in input_manager.ts and posted as "undo". That reaches undo, which queues a request, and on the next frame Store::undo applies the stored inverse as a new transaction labelled "undo: move rect". The reconciler moves the square back.

Every other feature reuses parts of this path. A slider scrub is the same loop with a preview in place of the optimistic transform (Part 5). A model edit enters at step 6 from TypeScript instead of from a drag (Part 7). Loading a file replaces the document and reconciles every node (Part 4).

Three things that look scarier than they are

Reading the Rust

Lifetimes: 'a, 'd, 'static. A lifetime is the compiler's name for “how long a borrowed reference stays valid”. fn live<'d>(doc: &'d Document, …) -> Result<&'d Node, …> at op.rs:199 says only that the returned &Node points into doc and can't outlive it. &'static str means a string baked into the program, such as a field name in a table. You can read past lifetimes almost every time.

Macros: anything ending in !. format!, vec!, write! build strings and lists. macro_rules! defines a macro: a code template the compiler expands before compiling. Two definitions matter here, id_type! and components!, and Part 2 expands both by hand.

Attributes: #[…]. #[derive(…)] generates code; #[serde(tag = "t")] tunes JSON; #[wasm_bindgen] exports a function to JavaScript; #[test] marks a test. Bevy adds #[derive(Resource)] and #[derive(Component)].

1.6Running it yourself

The store has no Bevy dependency, so it builds and tests natively. The workspace defaults to wasm, so pass your Mac's target:

cargo test -p iron_document --target aarch64-apple-darwin cargo run -p iron_document --target aarch64-apple-darwin --example dump

The second command runs examples/dump.rs. It builds a three-node scene, moves the rect, and prints the saved file, the view and the transaction side by side. Its output appears in Part 3. To drive the real app headlessly, use the /run-iron skill the model wrote. Its smoke.txt script exercises every exit criterion in the plan, and the screenshots in this guide come from it.

Before you go on
  • The document is the truth. Bevy entities are drawn from it and carry a Provenance(NodeId) tag back to it.
  • Everything that changes the scene is a transaction of ops. Undo applies the inverse ops as a new transaction.
  • Gestures move entities optimistically and write one transaction on release.
  • The store crate is Bevy-free. The bridge in src/document_bridge/ is where the two meet.
