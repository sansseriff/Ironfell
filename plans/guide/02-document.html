    What the document is made of

    This part covers the data, not yet how it changes. We start with the simplest document you could write, then add pieces one at a time. Each piece exists because the simple version breaks in a specific way.

    2.2Identity: NodeId

    A node's id is a number that means nothing: not its position, name or type. The store hands out the next number from a counter and never hands it out again, even after deletion. For display, the number is written in base62 (digits, then A–Z, then a–z) with a # in front. In the demo scene the group is #1, the twenty small rects are #2–#L, the dark square is #M (22), the circle #N, the slider #O, the bar #P, the torus #Q, the timeline #R, and the two clips #S and #T. You'll see these ids in the screenshots and views throughout the guide.

    There are two kinds of id, node ids (#…) and relation ids (r…), and they need identical code: printing, parsing, JSON. Rather than write it twice, id.rs defines a macro and invokes it twice:

    Reading the Rust

    macro_rules! id_type is a template. The first line says what the macro accepts: $name:ident is an identifier such as NodeId, $prefix:literal is a literal such as "#", and $(#[$m:meta])* means “zero or more attributes”, which is how the /// doc comment is passed through. Everything after => is pasted once per invocation with those names filled in.

    So id_type!(NodeId, "#") generates:

    • pub struct NodeId(u64); Note the field is not pub. Code outside the crate can't read or construct the integer.
    • from_raw and raw, marked pub(crate), so only the store itself can turn integers into ids.
    • Display (writes # + base62) and FromStr (accepts "#M" or bare "M").
    • Serialize/Deserialize, which write the id as its string form, so JSON files contain "#M", never 22.

    Keeping the integer private is deliberate: nothing outside the crate can depend on ids being numbers. If collaboration ever needs ids shaped like (actor, counter), only this file changes.

    The third id-like type, Version, is a plain newtype with a public field. It counts transactions: every successful one bumps it by exactly one.

    2.3The node record, and relations

    A node holds almost nothing itself. Its properties live in separate component tables (next section). The node is just identity, type and placement:

    • parent: Option<NodeId>. None means the node is a root. Placement is a field, not nesting, so moving a node into another group changes this one field.
    • order: OrderKey positions the node among its siblings (section 2.8).
    • tombstoned: Option<Version> records the version at which the node was deleted, if it was (section 2.9).

    A relation is any link between nodes that is not parent–child. It has its own id, a kind (RelKind) and a small data map. The one that matters today is Animates, which connects a clip to the node it drives (Part 6). Relations are stored in their own table and indexed in both directions, so “what does this clip drive?” and “what drives this node?” are both single lookups.

    2.4Values, and the slots that hold them

    A leaf is one editable authored value, such as “the square's x”. Every leaf holds a Value of a known kind:

    ValueKind is the “type tag” of a value, used to check that a Number field only ever receives numbers. Any is special: no value has kind Any, but a field can be declared Any to accept whatever kind its target has. Clip endpoints use this (Part 6).

    A leaf doesn't hold a bare Value, though. It holds a Slot, which is the answer to the fourth problem in the table above:

    • Slot::Const(value) is an authored constant: “x is 500.”
    • Slot::Bound(expr) is an expression over other leaves: “height is #O.slider.value * 300.” The slot stores the formula, never its result. Results live in the reactive graph (Part 5).
    • Slot::Animated(Reserved) is a placeholder that can never be created. The reason is below.
    Reading the Rust

    enum Uninhabited {} is an enum with no variants, so no value of that type can ever exist. Reserved holds one in a private field, which means no Reserved can exist either, and therefore no Slot::Animated(…) can ever be built.

    Why declare an impossible variant? The plan wanted the shape of Slot settled on day one: every match on a slot already has to consider “animated”, so adding the real thing later touches only the code that evaluates slots, not every place that reads one. In constant() you can see how such a case is handled: Slot::Animated(r) => match r._private {}. An empty match on an uninhabited value is Rust's way of saying “this branch can't run”, and the compiler accepts it as returning any type.

    Rough edge

    Step 6 ended up not using this variant. Animation became a layer in the reactive graph instead (Part 6 explains why, and the plan records it in §5.11). Slot::Animated is now reserved for nothing in particular, and the module comment at value.rs:5–7 still describes it as the future home of clip-driven values. The comment is slightly stale. The code is fine.

    The JSON form keeps the kind visible: numbers, bools and strings are bare, vectors are arrays, and colours, enums and refs are single-key objects ({"rgba": […]}, {"enum": "linear"}, {"ref": "#M"}). A binding is {"bind": "<expression text>"}. You can see all of these in the saved file in Part 3. The code is in Value's Serialize and Slot's Serialize.

    2.5Components: typed structs from one table

    Leaves are grouped into components, each a small named bundle: transform2d holds x, y, rot, sx, sy; fill holds color, opacity; and so on. A leaf's address is component.field, for example transform2d.x.

    The simple version

    One map per node, HashMap<String, serde_json::Value>. Adding a property means adding a key. But every reader has to check, at runtime and every time, that "x" exists and is a number. Typos are silent.

    What was built

    A Rust struct per component with one Slot field per leaf, plus a static table of field names and kinds. Readers get typed access; the validator, file loader, view renderer and model schema all read the same table.

    Writing twelve structs plus all their lookup code by hand would be long and easy to get inconsistent, so component.rs declares them all in one table and lets a macro generate the rest. This is the table: the whole vocabulary of what a node can hold.

    The leaf address: LeafPath

    A LeafPath is a component kind plus a field name. The field is a &'static str, a reference into the generated FIELDS table rather than a String of its own, which makes a path two small values that are free to copy. The only way to make one is LeafPath::new (or "fill.color".parse(), which calls it), and that rejects unknown fields with an error listing the ones that exist. An unknown path is an error, never a silent no-op. That rule, from vision doc 04 §9.4, recurs through every layer, all the way to the model's edit parser.

    When a leaf also needs to say which node, it becomes a Leaf { node, path } (defined in expr.rs:27). It prints as #O.slider.value, which is exactly the syntax expressions use to refer to it.

    2.7The Document: tables and indexes

    Now the container itself:

    It has two halves:

    • The tables (lines 72–77) are the actual data: nodes by id, components by kind and then by node, relations by id, the two id counters and the version. This is what gets saved.
    • The indexes (lines 81–86) are derived from the tables and exist only to make questions fast: a node's children in order, the roots, all nodes of a type, all nodes with a component, relations by source and by target. They're never saved; reindex() rebuilds them from the tables after loading.

    Components are stored by kind first (BTreeMap<ComponentKind, BTreeMap<NodeId, Component>>). That answers “all transforms” as one lookup, and in the saved file all transform2d records sit together.

    Reads are public

    Everything under the // ---- reads comment is pub and takes &self. These are the methods the rest of the app uses, for example:

    Writes are pub(crate)

    Every method that changes the document is pub(crate): callable from inside iron_document only. The Bevy app, the FFI and the tests can read the document but have no way to write it except by submitting ops. Vision doc 04's rule “no code path mutates the store directly” isn't a convention here. Code that breaks it won't compile.

    The mutators keep the indexes current as they go (insert_node updates by_type, children and the parent's child list). check_invariants cross-checks every index against the tables, and the tests call it after every transaction.

    2.8Sibling order without renumbering

    The simple version

    Store each child's index: 0, 1, 2, 3. Inserting between 0 and 1 means the new node becomes 1 and every later sibling is renumbered. One insert rewrites N nodes, and N nodes show up as changed to undo, to Bevy and to the model.

    What was built

    Each node holds a short string key. Siblings sort by comparing keys as strings. To insert between two siblings, the store makes a new key that sorts between theirs. No other node changes.

    Real values, from the store:

    CallResultWhy
    OrderKey::first()a0The starting key.
    after(a0)a1Appending increments the integer part, so ten thousand appends still fit in four characters.
    between(a0, a1)a0VNo integer fits between 0 and 1, so it adds a fraction. V is the middle digit of base62.
    before(a0)ZzUpper-case heads are the negative side, and they sort before lower case.
    after(az)b00The integer part outgrew one digit. The head letter says how long it is.

    The trick that makes this work is that the base62 alphabet 0-9 A-Z a-z is also in ASCII order, so plain string comparison sorts keys correctly. The first character encodes the length of the integer part (a = one digit, b = two…), which keeps a longer integer from sorting before a shorter one. After the integer comes an optional fraction, which is where “between” finds room. This is the published rocicorp/fractional-indexing scheme, hand-rolled.

    You don't need to follow midpoint, increment_integer or decrement_integer line by line. They are digit arithmetic, and the test at order.rs:307 pins their outputs to the upstream library's test vectors. The rule to remember: code outside the store never computes order keys. It asks for them with OrderKey::first/after/before/between, or, from TypeScript, document_place (Part 7).

    2.9Deletion keeps the record

    Deleting a node sets tombstoned = Some(version) and removes it from every index, so reads like children and nodes_of_type stop seeing it. The record and its components stay in the tables, which buys three things:

    • Stale references fail loudly. An op naming a deleted id gets “#M was deleted at version 5”, not “no such node”. You can see that message built at op.rs:203.
    • Undo restores the same id. Recreating a tombstoned id is allowed and counts as a restore (Part 3). Anything that referred to #M refers to it again.
    • Ids are never reused. The counter only goes up, and a tombstone keeps its number occupied forever.

    Garbage-collecting tombstones is deferred until the undo horizon makes it safe. Relations are the exception: unlinking really removes the row, and undo re-links it with the original id.

    Before you go on
    • Nodes have opaque, never-reused ids (#M). A node record is only type, parent, order key and tombstone.
    • Properties live in typed components, generated from one table by components!. A leaf is component.field, holding a Slot: a constant or a binding.
    • The registry says what each node type may hold. It's also exported as JSON for the model.
    • The Document's reads are pub; its writes are pub(crate), reachable only from the op applier, which is Part 3.
