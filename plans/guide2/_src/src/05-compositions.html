Compositions, figures and embeds

The central idea of vision document 09 is that one thing (a laser, a torus) can be drawn many ways, in many diagrams, and every drawing stays linked to the thing. This part covers roadmap stage C1 and the embedding work after it: composition roots, the figures relation, cross-highlighting and Link, and compositions shown inside other compositions (2D in 2D, 3D in 2D as a camera view, 2D in 3D as a plane).

The last sentence of that comment is the rule for this whole file: nothing is stored that can be computed. Which composition a node is in is found by walking up to the nearest composition root; which entity a node pictures is found by walking up to the nearest node with a figures relation:

figure_of walks up, which is what makes grouped figures work: clicking one wheel of a car that is a figure of a car entity finds the group, and the group's entity.

5.3Selection lifts through figures

Select the cartoon box and the torus lights up too, in another panel, because both are figures of one entity. Highlights are derived from the selection and the figures relations every time either changes:

The selection overlay (a separate view above each panel since stage H; Part 6) outlines what's in Highlights: a leaf by its shape, a group or embed by its frame, as in Figma. Plane views, which have no overlay, outline lit nodes in their content, and the 3D side reflects the same set into each mesh's outline state. Hover works the same way, which gives the "hover either, both light up" behaviour from the C1 exit.

Link, and the merge question

Link says "these two pictures are the same thing". Four cases:

  • Neither pictures anything yet: create an entity (and a thing definition and a model root if missing), and link both.
  • One does: link the other to the same entity.
  • Both picture the same entity already: nothing to do.
  • Both picture different entities: one of them must go, and the user (or the model) is asked which, never left to a guess. The question carries a summary of each entity (definition, parameters, figures, ports) so the answer is informed. Answering with keep moves the other entity's figures over and deletes it, all in one transaction.

"Show in" is the reverse journey: from a figure, find its counterparts' compositions and frame them (document_focus). A 2D view pans the node to its centre; a 3D panel backs its camera off until the node fills about half the view.

Two new views for the model

The tree view shows the document as stored. 5.4Compositions inside compositions

Later the user pointed out that compositions aren't really panels; like After Effects compositions, they can be placed inside other compositions. An embed node does that: a live reference, not a copy.

Embed a……inside a…Behaves like
2D composition2D compositionA group, clipped to a region (its frame, or the content's bounds)
3D composition2D compositionA camera view: a rectangle showing the 3D scene, through a named camera node or a derived view that frames everything
2D composition3D compositionA plane in 3D, textured with the 2D content
3D composition3D compositionA group (the obvious meaning; not yet needed)

Loops are refused when they'd be created: embedding A in B is rejected if A already shows B, directly or through its own embeds. The check runs on create, on changing the embed's source, and on reparenting, since moving an embed can close a loop too.

The main layout

The default viewer shows a composition named main, which is just embeds:

composition "main" (2d) embed "scene view" → scene at 0,0 (no frame: the scene's own bounds) embed "assembly view" → assembly at 815,10 200×350, a 3D camera view embed "pendulum view" → pendulum at 0,0 embed "controls view" → controls at 0,0 composition "assembly" (3d) mesh "torus" embed "card plane" → card a 2D composition as a plane beside the torus

So "everything in one view" and "each composition in its own tab" are the same document seen two ways. The pendulum and the level slider got compositions of their own when the tabs arrived (Part 8); main embeds them where they used to sit, so it looks as it always did.

Drawing and picking walk through embeds

The 2D layer draws a composition's nodes in painter order (the visible ones, from the spatial scene; Part 10). At each embed it recurses into the embedded composition through the embed's placement, clipped to its region; a 3D embed draws its camera's texture (Part 6) in the same painter order:

Picking mirrors drawing. It asks the spatial scene for candidates at the point, which already come with their chain inside the composition (Scene::chain); the pointer is mapped through each embed's inverse placement, and every hit records its chain: the nodes from the panel's top level down through every group and embed to the hit node. Part 7's selection rules are all about choosing a node along that chain.

Note line 165: an embed's own area is a hit too, marked background. It ranks below every shape hit, wherever the shape is. That ordering mattered when the pendulum moved into its own embed: the pendulum embed's region covers most of the scene, and without the rule, clicking a scene rect selected the transparent pendulum embed on top of it.

3D embeds: a camera per view

Every visible 3D embed becomes an EmbedView with a stable key (the panel id plus the chain of embeds that reach it), so its Bevy camera survives from frame to frame. The texture is sized to the embed's on-screen size, so it stays sharp at any zoom:

Without a named camera node, the view frames everything in the composition from a fixed direction, and only re-frames when content leaves the framed sphere, so dragging the torus doesn't make the camera chase it:

A 2D composition embedded in 3D is materialised as a plane mesh (materialize.rs:433), 100 document px per world unit, whose texture is the 2D content rendered off-screen (Part 6). Clicking on the plane intersects the camera ray with it and hands the 2D picker a point in the card's own space, so the card's shapes can be selected and dragged in 3D.

Rough edge

An embed without a frame takes its content's bounds, which shift as content moves, and its transparent background then covers whatever is beneath it in the parent. The background-ranks-last rule makes clicks behave, but the embed's region is still invisible to the user until hovered. A drawn frame (like Figma's frame labels) or a required frame on top-level embeds would make it explicit.
