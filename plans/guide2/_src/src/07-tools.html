7.1Which node does a click select?

The simple version

Select whatever is under the pointer. The innermost shape always wins. You can never select a group by clicking it, and dragging one arm of the pendulum drags just that arm out of the mechanism.

What was built (Figma's rule)

Select the outermost node whose container isn't open. A group is closed until you enter it; once something inside is selected, the group is open, so siblings are one click away. Cmd/Ctrl-click selects the innermost node directly. A double-click enters one level.

Part 5 showed that every pointer hit carries its chain: the nodes from the panel's top level down through groups and embeds to the hit node. Choosing a node is choosing an index into that chain:

Index 0 is the top level. A container at depth i is open if some selected node's chain passes through it. The one extra rule is the first clause: a top-level embed is always open, like a top-level frame in Figma (an artboard). That rule was forced by the demo: the whole scene sits inside one embed in Main, so without it every click would select "scene view". With it, clicking a rect selects the rect, clicking the embed's empty background selects the embed, and the pendulum (a group inside its own embed) selects as a whole.

chain: [pendulum view (embed), pendulum (group), ball] index 0: top-level embed → open index 1: group, nothing inside selected → closed → select the group double-click: the group is selected → enter → select the ball Cmd-click: select the ball directly Esc: up one level (ball → group → embed → nothing)

What a press does

A press has to be decided before anyone knows whether it's a click or a drag. The tool enters Gesture::Press, recording what a click would do on release and what a drag would become if the pointer travels more than three pixels (Part 13 draws the whole state machine):

The decisions match Figma's. Pressing an unselected node selects it at once and a drag moves it. Pressing an already-selected node in a multi-selection keeps the selection (so the drag moves them all), and only a click without movement narrows it to that node. Pressing an artboard's background starts a marquee over its contents; a click selects the artboard. Meshes in 3D, content on planes, sliders, path handles and shape handles become other kinds of manipulator in the same Gesture::Edit state; since October 15 there are no separate legacy drags, and selected meshes in a 3D panel get a transform gizmo.

A drag moves every selected node, each through Store::begin_drag (Part 3), so constrained nodes drag through their cluster and bound axes hold with their reason logged. The keyboard follows Figma too: arrows nudge 1 px (Shift: 10), Delete deletes, Enter and Shift+Enter go down and up a level, Tab walks siblings, Cmd+A selects all at the current level. Each is one transaction.

7.2The transform box

The box is the unit square mapped onto the selection: a node's own (oriented) box for one node, the axis-aligned bounds of every node's box for several. Grips are found in window pixels, so they stay the same size at any zoom:

Corners resize both axes, edges one, and the area just outside a corner rotates, with no separate rotation handle, as in Figma. A resize or rotation becomes one affine map A, in the panel's document pixels:

For a resize, the anchor is the opposite grip (or the centre, with Alt), and the scale is measured from where the press landed rather than from the grip's exact corner, so pressing a grip without moving changes nothing. Shift keeps the aspect ratio. A scale never collapses below one pixel. For a rotation, Shift snaps the node's final angle to 15°.

Turning A into leaf values

Every node the gesture affects is a Part, captured when the gesture begins:

For each part, A is moved into the node's parent space, Q = P⁻¹·A·P, and composed with the node's own transform and its box. The result is decomposed back into position, rotation and size:

What gets written depends on the kind of node, which is the important design choice. Resizing a rect writes its size, not its scale, so its stroke keeps its width (Figma's behaviour, and why the shadow rect resizes cleanly). An ellipse writes its two radii about its centre, so a circle stretched along one axis becomes an ellipse. A 2D embed's resize changes its window (its frame) and leaves the content where it is. A path transforms its packed anchors, or its expanded points and handles:

Dragging past the opposite edge flips the node by negating its sy. Every leaf is previewed through its handle each frame (preview_writes), so a locked leaf simply holds still, and the whole gesture commits as one transaction labelled "resize rect" or "rotate 3 nodes".

The box is not in the document

The box, the grips, the hover outline and the marquee are drawn into each panel's Overlay view, a separate retained texture above the panel's content (Part 6), rebuilt from the selection when it changes:

Rebuilding this small list re-renders only the overlay texture, never the document's content. The geometry it draws (frames, grips, lit outlines) is cached in SelectionGeometryCache, keyed by the view's composition revisions (including embeds), selection reaches and interaction state. An unrelated Stats composition tick no longer invalidates its geometry. Chrome sizes and colours come from the view's resolved context fields (Part 14).

7.3What the shell had to start sending

The tools needed input the canvas never received before:

  • Modifier keys. Alt and Cmd never arrived as keys. Every pointer, wheel and key event now carries modifier bits (Shift 1, Ctrl 2, Alt 4, Cmd 8) through engine_api::set_modifiers.
  • Tool keys. The shell routes editing/navigation commands and suppresses browser defaults. View tool keys are resolved from contexts, then sent as commands (toolKey), not raw keys, so browser behaviours like Tab focus and Cmd+A text selection are prevented.
  • Where a press happened. On a slow frame, the press and the first moves of a drag land in the same frame. A press now carries its own position (left_bt_down_at), and later moves wait for the next frame, so a press is resolved where it happened.
  • Cursors. The canvas lives in a worker, which can't set a cursor, so Rust sends the cursor it wants (EngineEvent::Cursor, through the shared event union) and the main thread sets it. CSS has no rotation cursor, so rotate:<degrees> becomes a small SVG arrow turned toward the corner.

7.4Shapes, packed paths and editable points

A path usually holds all contours in one path.d geometry value. Each contour has closedness and anchors with relative handles. Value::Geometry shares immutable data through an Arc, with outlines and bounds cached on first read; cloning a transaction does not copy every anchor. Schema 8 stores six numbers per anchor, preserving handle bits rather than round-tripping SVG text.

When points need independent identity for editing, binding or constraints, contour::expand_points returns ops that clear the packed value and create contour/point nodes in one transaction. Selected-path point editing performs this expansion; the pen still authors individual point nodes. Both representations use the same contour reader, renderer, picker and SVG exporter. Moving an expanded point is a local geometry change of its path.

Shapes follow Figma's model (October 14). A rect (with optional corners) and an ellipse (with optional arc: start, sweep, inner ratio) keep their parameters, so they stay editable, bindable and constrainable; a lone selected shape shows dots for its corner radii or its arc. iron_document::shape computes their outlines as anchors with handles, the same form a path's points take. Editing a shape point by point first converts it to a path: a Delete and a restoring Create of the same id in one transaction, which keeps its placement, paint, name and relations. What can't survive is anything that reads or drives the old parameters (a binding on size.w, a clip on radius.rx). Those are cuts, and the shell asks before making them.

The pen

Each placed point is one transaction, so undo removes one point. The first click creates the path, its first contour and its first point together; later clicks add a point to the last contour; a click back on the first point sets contour.closed:

The point's handles come from the drag between press and release, so a click is a corner and a click-drag is a smooth point. The transaction is pushed only on release, which is why the pen never needs to preview a node that doesn't exist yet. While drawing, the overlay draws the path's points, the line from the last point to the pointer, and the handle being dragged; none of that is stored.

When a lone path is selected with the select tool, its points and handles are drawn and take the press before the box's grips. A point drags through begin_drag like any node ("move point"); a handle writes the point's handles leaves, mirrored to the opposite handle unless Alt is held ("move handle").

7.5The inspector

The right-hand panel shows the first selected node's facets and fields. Rust describes the node, including how an edit to each field would land:

A field shows its value as a reader sees it, its binding if bound, and its handle: direct, via a linear binding's source, or locked with the reason (shown as the field's tooltip, with the input disabled). Setting a field parses the text by the field's current kind (number, colour, vector, quantity) and applies it through the handle as one transaction, "set size.w" (Store::set_through_handle, which leaves a running drag alone unless the edit conflicts with it; Part 13). Number fields can also be scrubbed by dragging their label, which runs a real store gesture with a token. So setting the shadow's bound x to 720 moves the square to 620, through x = #square.x + 100.

What it isn't yet

This inspector is HTML generated from a JSON description. The design note (plans/specs/panels-and-session.md) makes it a composition in the session whose controls are nodes bound to the target's leaves. The semantics are already the same (edits go through handles, locks say why). What's missing is hosting document nodes as HTML, which Part 8 discusses.

7.6Snapping and smart guides

iron_spatial::snap supplies edge/centre candidates and a latch with hysteresis in screen pixels. Moving, resizing, path points and the pen use it. Smart guides are overlay geometry, not stored constraints. View contexts supply whether snapping is enabled and its tolerances; the shape tools and equal-spacing labels remain follow-ups.

7.7Text is drawn and edited on the canvas

A text node has content, font, style runs and sizing (auto width, auto height or fixed). iron_text shapes and measures text; iron_document::text::measure gives bounds, picking, renderer and caret one layout. The display list supports glyph runs. Font catalog entries load on demand through the host; native also discovers installed fonts. New font availability triggers remeasurement and layout.

The text tool and double-click enter editing. A hidden HTML input handles text/IME and UTF-16 selection offsets; Rust owns the canvas selection, movement and transaction edits. The Text inspector can style selected ranges. Content may be bound, including fmt readouts for quantities, so a live electrical voltage label is an ordinary text binding.

7.8Layout and tables

A group's layout facet chooses horizontal/vertical stack or grid, gaps, padding and alignment. Children's layout_item leaves choose fixed/hug/fill sizing, tracks, spans and absolute placement. iron_layout wraps Taffy; the document's layout producer publishes resulting positions and chosen sizes as runtime signals (Part 12). A laid-out position is therefore locked against a plain move, while a sequence affordance can reorder items and preview the new flow. Motion eases that preview without storing intermediate positions (Part 14).

A table contains row nodes whose cells are text nodes. Merges use row/column spans; layout computes explicit grid areas, and table decoration draws bands and rules broken around merged cells. Boxed/light presets, row and column edits, spreadsheet paste, a canvas tool, inspector and model <table> markup all use transactions. Style inheritance remains deferred.

Still open

Group/ungroup, drag reparenting and inserting points on segments remain in plans/specs/select-tool.md. Text and layout have additional limits recorded in their specs; the inspector is still HTML, with context-driven section order, rather than a session composition of hosted controls.
