Who computes where things are

Up to Part 9, three different pieces of code each worked out where a node sits on screen, and Bevy's was the one that drew. On October 17 that was settled the other way round: Iron computes every world transform, and Bevy only receives them. That one decision changed what the store tracks, gave the spatial index a different shape, removed Bevy's transform tree for document nodes, and removed most of the entities. This part follows the four commits that did it (161648c, 26de602, 1cbe2d1, and the signal layer of Part 12), with the data structures each one introduced.

10.2Why the store: transforms sit in the middle of the graph

A world transform isn't only an output for drawing. The solver reads the world position of a constraint's anchors, a binding can read a solved leaf, a clip can drive a leaf that the solver treats as known, and a binding can read the result again. Here is one chain built from pieces the demo scenes already have:

The project had already hit this once: when Bevy owned the drag, nothing bound to a dragged shape moved until release, and the fix was to move drags into the store (Part 3). Vision 10 states the general rule: the evaluator lives in Iron; producers live wherever fits (Part 12). It doesn't say Bevy is the wrong place for physics. A dynamics engine over a population of bodies is a producer; dragging a constrained assembly with one undo step is a document operation.

One small consequence: Iron computes in f64. An f32 at document coordinate 1,000,000 resolves to about 0.06 px, which an infinite canvas reaches. Bevy receives f32 only at the end.

10.3Revisions: the store says what kind of thing moved

The simple version

Recompute the world bounds of every node that changed. When you rotate a group, every descendant's world bounds change, so "every node that changed" is the whole subtree, and the 10k rotation costs 10k bounds.

What was built

Classify each change. A node's own transform2d moving is a placement change: its descendants' bounds, in its own space, didn't move. Its own size, radius, stroke or outline moving is a local change. Creating, deleting, reparenting or reordering is structure. An index that keeps each group's contents in the group's space then rewrites one entry for a rotation.

10.4The spatial scene: a tree of indexes

iron_spatial::Scene mirrors the document's groups. Every node with children that hold 2D content gets a scope: one R-tree (BoundsIndex, over understory_index) of its children, in its own local space. A group is then an entry in its parent's scope whose bounds are its own scope's union mapped through its affine.

Updating: placement versus local

Each frame, prepare_spatial calls Scene::update, which takes the store's changes and branches on their kind:

Structure rebuilds everything (222–225); the scene can't patch painter order or chains cheaply, and structural edits are rare. A local change recomputes one leaf's bounds from Store::local_bounds (247–248). A placement change of a group (273–280) is the case the whole design is for: the group's subtree union is already in its child scope, so its entry in the parent scope becomes that union under the new affine. Nothing below it is touched. Then settle carries changed unions upward:

Dirty scopes are processed deepest first (290). After committing a scope's R-tree, if its union changed, either the scope is a composition, in which case every frameless 2D embed showing it must grow or shrink (306–311), or it's a group, whose entry in its parent is rewritten and the parent marked dirty (312–317). So a dragged leaf costs one entry, and up to its depth more only when it pushes a union outward.

Querying: map the question, not the content

A point or rectangle query descends the same tree. At each group entry it hits, it maps the query into the group's space through the inverse affine, rather than mapping the group's content out:

The same scope tree answers the other question readers need, "what is this node's world affine?", in O(depth) without walking any content: placement(scope) multiplies the group affines above a scope, and world_affine(id) = placement(entry.scope) · entry.affine.

Native numbers for the stress shape (100 cells of 100), from tests/scene.rs: rotate update 24 µs, one leaf drag 25 µs, a 1600×1000 visible-rect query 142 µs for 405 hits, structural rebuild 40 ms. In the app, the bounds phase fell from 24.8 ms to under 0.1 ms for the 10k rotation.

Reading the code

prepare_spatial (spatial.rs:33) calls bypass_change_detection() on both the scene and the store before updating. Bevy marks a resource changed whenever a system takes it mutably, and the 2D layer rebuilds its display lists when the scene is changed. So the system compares generation before and after and calls set_changed() only when something moved. Without that, every idle frame would rebuild every view.

Rough edges

Stale comments. The module comment at the top of document_bridge/mod.rs still says a drag "moves the entity's Transform each frame for latency"; that stopped being true in Part 3. The comment in spatial.rs still says drawing and picking take placements from Bevy and that the drift check stays; both ended with 26de602. rendering/architecture.md §1 still lists "Bevy entities, transform propagation" as a pipeline step. The code here is the reference.

The selection overlay's cache (SelectionGeometryCache, Part 7) is still keyed on the global GeometryRevision, so any change anywhere rebuilds the selection's box and outlines. With Part 12's producer publishing every frame, a ticking gauge invalidates whatever is selected. Keying it on the selected subtrees' revisions (chain_stamp plus local revisions) is the render handoff's open item 3.

The store itself caches no world affine. Store::world_affine still walks the chain each call; the scene caches placements per group, which is what the 2D readers use. 3D world affines are recomputed per write.

A picker runs a little before the scene updates. Picking runs in PreUpdate, but prepare_spatial runs in PostUpdate. So a transaction applied by this frame's sync reaches the picker's placements next frame. Picking re-runs whenever the version changes, so this shows only as one frame of staleness for nodes the sync just moved.

Before you go on
  • Iron computes every world transform, in f64, because transforms sit inside the one dependency graph the store evaluates. Bevy receives 3D world affines and nothing for 2D.
  • The store classifies each change as placement, local or structure (geom::Revisions). The reconciler and the spatial scene each have their own drain, so neither starves the other.
  • iron_spatial::Scene keeps one R-tree per group in the group's own space. A rotation rewrites one entry; queries map the question down through inverse affines.
  • Draw data lives in Drawables by NodeId. Entities exist for 3D nodes and for the Live working set (selection and hover, within a budget), and they're flat.
