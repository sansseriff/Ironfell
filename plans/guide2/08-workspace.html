    The workspace and the session

    The main view had become crowded, and the left panel was a card of leftovers. This part covers the shell's answer: a dock of tabs and splits where every tab is a view onto a composition, drawn by the canvas, by HTML, or both; per-view pan and zoom; and a third tier of state, the session, for things like the selection that belong in the store but not in the file or the undo history.

    You needPart 5's panels; Part 6's views and textures.
    Filessrc-ui/views/{views,workspace}.ts, src-ui/views/{Workspace,ViewPanel,AddViewMenu,Toolbar}.svelte, src-ui/views/html/*, src/panels.rs, bevy_app/select.rs (navigate_views, sync_session_selection), iron_document/src/{id,document,lib,serial,view}.rs. Design: plans/panels-and-session.md.

    8.1A panel is a view

    The design discussion settled on one definition that holds whether a panel shows canvas pixels, HTML, or both:

    The idea

    A view is a source plus a notation. The source is what it shows: a composition, the timeline root, the document, the session's selection. The notation is how it's drawn, and decides which part the canvas draws (a Rust panel kind) and which part is HTML (a Svelte component). A presenter is where the view sits: today a dock tab or split; later a popover, a context menu, a tooltip. The view doesn't change with its presenter.

    The Document, Model and Inspector tabs are HTML views; Main, Scene, Pendulum and the rest are canvas views of compositions; the Timeline is a canvas view of the timeline root. A hybrid (an inspector with canvas sliders and HTML text fields) is a notation with both parts; the HTML is laid over the canvas part and takes the pointer only where it actually draws something.

    On the Rust side, nothing about tabs exists. Whatever part of a visible view the canvas draws arrives as a panel rectangle, exactly as before:

    8.2The dock

    Tab and split UIs are mature in HTML (VS Code is one), so the dock is dockview, a framework-independent library. Each dockview panel renders a ViewPanel, which mounts the canvas part only while its tab is visible:

    Because a hidden tab unmounts its placeholder, Rust removes the panel, the panel's camera and view stop, and a hidden tab costs nothing to render. The default layout puts the compositions in tabs in the centre, Document and Model on the left, the Inspector on the right and the Timeline across the bottom:

    The layout is workspace state: saved in the browser (iron.workspace.v4) and restored on reload; ?layout=default or Reset layout in the Document tab forgets it. It is never in the document or its undo. "+" in any tab bar opens any composition (Rust lists them through document_compositions) or a fixed view.

    The dock floats over the canvas

    The dock is HTML over the one full-window canvas. Its chrome must take the pointer (tabs, sashes, HTML views), and everything over a canvas view must let it through to the canvas, except while a tab is being dragged, when drop targets over canvas views must see the pointer:

    Tab drags use pointer events rather than native HTML drag-and-drop (dndStrategy: 'pointer'), which is unreliable in Safari and hung the test browser.

    Rough edge

    dockview's ESM build ships without its stylesheet, so src-ui/views/dockview.css is a copy extracted from the UMD bundle of version 8.5.1. Upgrading dockview means regenerating it.

    8.3Pan and zoom per view

    Every 2D view has its own pan and zoom in ViewCameras, keyed by view id, and PanelView::affine (Part 5) carries them to drawing, picking, the select tool and 3D embed textures, so nothing else had to change. The controls are Figma's:

    Scrolling pans; Ctrl/Cmd+wheel or a trackpad pinch (which browsers send as Ctrl+wheel) zooms about the pointer, keeping the document point under it fixed (pan_keeping); Space-drag pans; Shift+1 fits the content, Shift+0 is 100%, Cmd/Ctrl +/− zoom about the centre. "Show in" (Part 5) now sets the pan and keeps the zoom. The 3D camera controller acts only on the view under the pointer, so Space and the wheel no longer fly a camera in another tab.

    8.4The session tier

    The selection used to be a Bevy resource: invisible to bindings, to the model, and to anything that should be able to read "what's selected". Moving it into the store raised a question with three answers:

    TierHoldsSavedUndoShared
    DocumentContentyesyesyes
    WorkspaceLayout, pins, pansyes, beside the documentnono, per user
    SessionSelection, hover, the playhead, inspector contentnoselection, laterno

    All three are meant to live in the store and speak its language (nodes, relations, bindings); they differ only in the rules their roots impose. The session tier is built; the workspace is still in the browser.

    Its own id range

    The simple version

    Create the session nodes like any others. The first selection takes the next id, and every content node created afterwards gets a different id than it would have, so saved files, smoke scripts and the model's references all shift depending on whether someone clicked first.

    What was built

    Session ids start at 2⁴⁰. Session nodes and relations are allocated from their own counter, so content ids never move. Anything at or above the base is never saved and never shown in the tree views.

    Applied without a transaction

    Every op must be in the session range (a content op is refused). The ops apply directly, with no version bump, no history entry and no undo; on an error the ops already applied are rolled back through their inverses. session_version counts session changes for whoever needs to notice them.

    The selection is relations

    A selection is a selection node under a session root, with one ordered selects relation per selected node. Relations, not children: a child is owned and placed by its parent, and a selected square stays where it is. Each relation's data records how the select tool reached the node: the panel and the chain (Part 7), so a selection made in Main through the scene's embed is restored to the same place.

    In the app, the select tool keeps working on a per-frame copy (SelectionState plus its reaches), and one system keeps the copy and the record in step:

    The model now receives the selection with every request, as a SELECTED block before the instruction (agent.ts:30), so "make the selected one red" resolves; __iron.session() returns it for tests.

    Not yet

    Selection in undo, Figma-style: an edit remembers the selection before and after it, and runs of selection changes merge into one undo step. The representation is ready for it; the merging isn't built. Nor is the workspace root, or the inspector as a session composition with controls bound to the target's leaves. The missing piece for that last one is hosting: rendering document nodes (a text field node) as HTML elements laid over the canvas at rectangles Rust computes, which the original spine plan designed (§4) and nothing has built yet.
