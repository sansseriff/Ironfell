Behaviour as data

Until October 26 every choice about how Iron behaves was a line of Rust: “a row is passed through”, “a slider scrubs”, “R is the rectangle tool”, “the inspector shows Position before Fill”, “grips are 8 px and blue”. This part covers the change that turned those choices into data: contexts, lists of rules the engine reads, with the built-in ones shipped as a read-only library and a document free to override them. It opens with a one-page map of the whole app as it stands, so you can see where contexts sit, then walks the change from the vocabulary up: how a value is resolved, where rules come from, what the select tool asks, what each view offers, keys, reordering and motion, interaction state, chrome, and what is left.

14.1The app today, on one page

Four layers, top to bottom. Each talks only to its neighbours, and every arrow that changes the document passes through one door: a transaction applied by the store.

One frame, briefly (Part 11 has it in full): the host delivers pointer and key input; the tools turn it into previews or transactions; the store applies, re-derives bindings, solves, lays out and, if motion is on, eases what layout moved; the bridge syncs changed nodes to the spatial scene; each view re-encodes what changed; the overlay draws chrome on top; events go back to the shell. Contexts add two steps to that frame: publish_interaction_state (what is hovered, selected, pressed or dragged) and view_focus_system (what each view offers), both cheap and both skipped when nothing they depend on changed.

14.2The idea: choices are data, mechanisms are code

Before

The select tool asked what type is this? and branched: "row" is passed through, "slider" scrubs, "group" | "use" light as frames. The shell hard-coded v p r o t as tool letters and the inspector's section order. A new notation (a schematic, a deck) would have meant new branches in each of those places.

After

The tool asks what does this node afford? and a resolver answers from rules: resolver.get(chain, i, Field::SELECT) → "through". The rules for today's behaviour live in std_contexts.xml, read-only. A notation is a named bundle of rules; a document can override one field for one container without touching code.

The user's principles, which every piece below follows:

PrincipleWhat it means in the code
Human-interface choices are data, even the built-in onesEvery default the tools read is a rule in std_contexts.xml or a field's registered default, never an if on a type name. The admission test: a field is added only together with the mechanism that reads it.
Built-ins are never savedThe library is embedded in the binary (Library::builtin). Saving a document writes none of it.
Documents save only overridesA document context node holds markup that adds rules over a built-in of the same name, or defines a new context. Inline affords facets are one-node exceptions.
No deep inheritanceA node's values come from its notation, itself, and its direct container. Never a grandparent. extends is one level.
The shell follows the view's contextToolbar, keymap, inspector sections, tolerances and chrome are view fields, resolved per view and sent to the shell as an event.

14.4Contexts and rules

A context is a named list of rules. A rule matches by position relative to the node carrying the context (self, children, all = both, or view), optionally by type (type:rect|ellipse) and state (state:hovered), and declares field values. Within a context, later rules win, field by field. A context is carried two ways: a composition's notation names one (free → std:free-2d), and a container type can carry one by for, with a leaf test when the type alone is not enough (a stack is a group with layout.mode=stack_y):

That is the whole of what tables and stacks do differently from groups. A row is through, so a double-click on a table reaches a cell; a table navigates as ARIA's grid; a stack's items reorder by drag and glide when layout moves them.

14.5Resolving a value, locally

The resolver is asked about a node along a chain: the path of containers a view reached it through (a node in an embed or an instance has a different chain in each view). Four layers apply, weakest first:

__iron.computed(id) (and the model's computed read) prints the result with provenance, so “why does this cell edit on double-click?” has an answer you can read:

affords.select="target" affords.select.by="std:free-2d rule 1" affords.enter="edit" affords.enter.by="std:table rule 1 from #…" affords.edit="text" affords.edit.by="std:free-2d rule 7" affords.grips="box" affords.grips.by="std:free-2d rule 1" affords.drag="point" affords.drag.by="std:free-2d rule 1" affords.drives=""

A field with no .by holds its registry default. “std:table rule 1 from #…” names the document's context node whose rule was appended to the built-in std:table.

Reading the code

container() calls values() on the nodes before it to find out whether each is through, so resolution is recursive along the chain. Chains are short (a handful of nodes) and the select tool resolves only the chain under the pointer, so this has not needed a cache; the hover-sweep checkpoint stayed at 1.3 ms through every step.

14.6Where rules come from, and what is saved

The inline style is CSS-like: field: value pairs separated by semicolons, an unqualified name meaning affords., a qualified one any node field (chrome.handle: dot). It parses into an ordinary rule with an INLINE source.

14.7What the select tool asks

A press asks its questions in this order. None of them names a type:

Controls are the most interesting branch, because they make any plain node a widget. A press on the Dials tab's needle (affords.style="drag: ring; drives: transform2d.rot") turns its own rotation leaf, and that leaf is bound to a slider (rot = level × π), so the store inverts the binding (Part 3) and the slider moves. A leaf that cannot follow (bound non-linearly) is refused with the handle's reason, and the press does nothing.

The same mechanism gave demo 4, the Data tab: three sliders shown as a table of readouts ({= fmt(#s.slider.value * 100, 0)}) and as bars. A bar's drag drives its bound height; typing into a readout cell edits the slider, because words bound to fmt, str or sci now invert through their number (handle.rs, typed_number: the typed text is parsed, a plain number taking the format's unit). The binding stays.

Rough edge

track along a path (a bead on a wire) is deferred: a plain node has no leaf of its own holding its parameter, and its bound x and y are not linear in anything, so the own-leaf rule refuses it. It arrives with a component whose instance has an input to drive.

14.8Each view's focus: what the shell shows

View fields are resolved against a focus, not a node: the composition the view's tools create into, the containers the selection is open in, and the view's states (editing-text, editing-points, main where a component's main is). The notation's view rules apply first, then those of the open container's context, so entering a table could change the palette.

Plain letter keys no longer mean anything in the shell. route_tool_keys turns a letter into tool:<id> through the keymap of the view under the pointer (or the last one it was over), and drops a letter that view does not bind. So in the Pitch tab, B makes a table and R does nothing, while in Main R is the rectangle: same app, different data.

14.9Keys, reordering and motion

Keys. keys.nav on a container gives its items ARIA's composite behaviour. interaction::key returns a KeyAction the tool performs: in a grid (a table) arrows move cell to cell over merged cells, Tab past the last cell adds a row, Enter edits; in a list-y (a column stack) Down selects the next item and Alt+Down moves it (one Reorder). A container that does not navigate returns None, and the key keeps its canvas meaning (nudge).

14.10Interaction state

Hovered, selected, pressed and dragged are facts the host knows. Each frame publish_interaction_state hands them to the store (Store::set_interaction, a no-op when unchanged), where two things read them:

  • Rules may match a state: <rule match="type:rect state:hovered" …/>. The resolver sees the states through store.resolver().
  • Bindings may read a node's state if it opts in with an interaction facet; a producer named interaction publishes interaction.hovered and friends as runtime values. Pitch's card does this: fill.opacity = {= #card.interaction.hovered ? 1 : 0.45}.

A binding that reads interaction state may only drive how a node looks (appearance, fill, gradient, stroke, shadow); anything else is refused at apply time as out_of_scope. Otherwise hovering could move geometry, which would move what is hovered: a feedback loop through the pointer.

14.11Chrome

The plan (chrome.md) imagined chrome (selection boxes, grips, outlines, handles) as pictures: session nodes drawn over the view, defined as data, picked like content. What was built is the first, cheaper layer of that: chrome's choices and looks are context fields, and the existing overlay drawer reads them.

Chrome as nodes

Every hover frame would create and delete nodes in a session composition, re-run the graph and invalidate render caches. The overlay is today a cheap retained layer (hover-sweep 1.3 ms); that churn would put it at risk, for no gain until a notation needs chrome of a different shape.

Chrome as fields

View fields chrome.accent, grip, grip_shape, hover go into each view's Offer; node fields chrome.lit and chrome.handle are resolved per lit node. The defaults draw exactly what was drawn before: an accent replaces the built-in blues only when a context sets one.

Rough edge

Path points, ports, guides, empties' markers, component chips, the marquee and tool previews keep their built-in colours. chrome.hover="off" stops hover from lighting, not from being tracked: the interaction state still says hovered. A part's handle dot is looked for among a lit container's first 64 children, and which chains are dotted is cached by document version, chains and interaction states: the first version resolved them every frame and cost 0.7 ms a frame with a 10k group hovered, which the same-day A/B benchmark caught.

Recap

The engine now holds mechanisms (picking, gestures, a resolver, layout preview, an interpolator, the overlay) and the choices are rules: built in and never saved, overridden sparsely by a document, resolved locally from notation, self and one container, with provenance. Views resolve their own fields from a focus and tell the shell what to show. A model can read computed to see why something behaves as it does, and write a <context> to change it.
