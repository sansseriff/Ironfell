    Runtime signals and producers

    F3 described a stack of layers that every read goes through: overlay, binding, physics, clips, constant. Two of those were special-purpose maps, and a planned simulation would have been a third. Phase 4 of vision 10 (50b36f1) replaced them with one runtime layer of signals, each owned by a producer. Clips and the port network became the first two producers. A Bevy system became the third: 160 gas particles that have no document nodes, push on a piston, and publish a pressure the document's bindings read like any value. This part covers the layer, the publish algorithm, freezing, and the demo.

    You needF3 (the graph, read_with, clips), Part 9 (the across/through network), Part 10 (Iron owns world transforms), Part 11 (the frame order).
    Filesiron_document/src/graph.rs, lib.rs (publish, freeze, register_producer, resample, resolve_physics), handle.rs, document_bridge/gas.rs, demo.rs (piston); tests in tests/signals.rs, smoke script piston.txt.

    12.1One map per source doesn't scale

    How it was

    A map per source. The graph held animated: Leaf → Value for clips and physics: Leaf → Value for the network, and read_with checked each in turn. Each new source meant a new map, a new branch in the read order, a new case in handle ("locked because…"), and a new rule for what happens when two sources claim the same leaf. A Bevy simulation or a Model session would each have needed one.

    What was built

    One map of Signals, each tagged with who published it. A producer replaces its whole set of values each time it publishes. A leaf claimed by two producers keeps the first claim and reports the second. A bound leaf can't be driven at all. Bindings read a signal exactly as they read a constant, and nothing in the layer is ever saved.

    12.3Publishing: replace your whole set

    A producer publishes everything it holds, every time. The graph diffs that against what it held last time:

    1. Bound leaves are refused (139–142): a formula wins, and the attempt is recorded in signal_errors.
    2. The first claim wins (144–147): a leaf held by a different producer stays with it, and the newcomer gets an error. A leaf the producer re-publishes with the same value is restamped but not reported as changed.
    3. What it stopped naming is released (159–164): the difference between last time's held set and this time's.
    4. Only moved values propagate (173–181): each changed leaf is noted, unless a gesture is previewing it, and its dependents are invalidated in height order, as for a constant that was set.

    A host publish isn't an isolated write. Lines 410–413 re-solve every constraint cluster live and then the network, so a signal that feeds a cluster's input moves the mechanism in the same call, and a signal that feeds a network parameter moves its solution. This is the "one evaluator" of Part 10 in practice: producers supply inputs, and the store propagates them through bindings, clusters and the network in one place.

    The network is also a producer that reads its own last output: its initial guess for each unknown is the signal it published last time (x0 in resolve_physics), so successive solves start warm.

    A 3D composition cylinder holds a translucent chamber (a unit cylinder scaled to radius 0.6, length 3, along X), a piston disc, and a rod. A 2D composition piston embeds the 3D view next to a stroke slider and two gauge bars. The document side is ordinary bindings:

    Three details from that excerpt. The targets are found by name and cached per document version (154–157), so an edit elsewhere doesn't re-search every frame. The producer runs only while some panel or embed shows the cylinder composition (167–170), so a hidden demo costs nothing. And it runs before sync_document: the publish's changes are drained by the sync right after it and reach the screen this frame, together with everything else.

    The physics check: compressing the gas with the slider raises the pressure bar, and the P·V bar (pressure × gas length) stays level. That's Boyle's law, and it holds only if the gas really is isothermal, which elastic walls guarantee. __iron.signals() lists producers, signals and conflicts; __iron.producer('gas', 'freeze' | 'stop' | 'run') drives it.

    Rough edges and open questions

    One host producer, by name. engine_api::document_producer knows only "gas"; a second Bevy producer needs a registry of running producers on the host side.

    No collisions with document shapes yet. The "Live + simulating" mode (Part 10), a physics engine acting on Live document entities and publishing their poses, isn't built. The publish it would use is the one shown here.

    Within one producer, nothing is checked. Two clips aimed at one leaf both go into the clips producer's single map, and the later one silently wins (F3's rough edge still holds). Conflict detection is only between producers.

    Open (vision 10 §8). Q1: does the kinematic simulation of CS §11 run in iron_solve or as a Bevy producer? Q4: should the model's view of a leaf name the producer behind its value?

    Before you go on
    • Reads go overlay → binding → runtime signal → constant. Clips (0), the network (1) and host systems (2+) are all producers of the one runtime layer.
    • A producer publishes its whole set each time; the graph releases what it dropped, refuses bound leaves and other producers' leaves, and propagates only values that moved.
    • A published leaf is Locked to gestures, naming its producer. freeze turns a producer's values into one undoable transaction.
    • The gas reads Iron's poses, keeps 160 particles with no document nodes, and publishes one number before the sync, so the document stays the only thing that's saved or undone.
