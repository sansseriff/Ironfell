Drags through the store

In the first guide a drag moved the entity every frame and wrote one op on release. That was enough for a square on its own. It isn't enough once a shadow is bound to the square (the shadow should follow during the drag, not after), or once the dragged value is itself bound (y = 640 − 300·v, where dragging should set v). This part covers roadmap stage A: world transforms inside the store, handles that invert bindings, and previews that reach the screen in the same frame.

Filesiron_document/src/{geom,handle,lib}.rs, document_bridge/mod.rs (reconcile_gesture, DocumentChanges), bevy_app/mod.rs. Parts 10 and 13 continue this part: who owns transforms, and what happens when another edit arrives mid-gesture.

3.1What the old drag got wrong

The simple version (the first spine)

Move the entity now, write the op on release. The square follows the pointer, but its bound shadow reads the document, which hasn't changed yet. So the shadow sits still for the whole drag and jumps on release. A rect whose x is bound can't be dragged at all.

What was built

A drag previews values in the store, never entities. Every frame the pointer's position becomes a preview of the right leaf. The reactive graph re-evaluates everything bound to it. A same-frame reconcile pass rewrites the affected draw data before anything draws. Nothing in a drag writes a Bevy Transform; since October 17 most 2D nodes don't even have one (Part 10).

Three pieces make that work: the store must know where a node is in the world (to turn a pointer position into an x), it must know which leaf a drag should write (the value itself, or a binding's source), and the bridge must apply the preview within the frame.

3.2World transforms in the store

The solver (Part 4) and the gesture code run inside the store and need to know where a node is without a round trip through the ECS. Stage A added geom.rs to compute it. At first this was a second copy of what Bevy computed for rendering, checked against it every frame; since vision 10 it is the answer, and Bevy receives it (Part 10):

Two details. Values are read through read, the same reader the reactive graph uses, so previews, bindings and clips are all respected: a node mid-drag is where the preview says. And the composition order (translate, rotate, scale; parent before child) is exactly Bevy's, which a unit test checks with glam, so 3D poses handed to Bevy and the old entity transforms agree. The same file now has Affine3 and world_affine3 for 3D, the revisions of Part 10, and local_bounds, a drawable node's extent in its own space.

Reading the Rust

chain.iter().rev().fold(Affine2::IDENTITY, |acc, &n| acc.then(local_affine(doc, read, n))) walks the parent chain root first, starting from the identity and composing each node's local transform onto what's accumulated. fold is a loop with an accumulator; |acc, &n| destructures the borrowed id so n is a plain NodeId.

The decision:

Read it top to bottom:

  1. A leaf of a component the node lacks but its type allows (a rect's corners before any corner was rounded) is Direct (40–47): the gesture drives it and its commit adds the component (Part 13).
  2. A leaf a producer holds is locked (49–55), with a reason naming the producer: a clip, the physics network (Part 9) or a host producer such as Part 12's gas. Its value isn't the user's to set right now.
  3. A constant is Direct. A bound leaf continues, and so does an in-port whose signal a connection derives (58–60, Part 9).
  4. inline substitutes every bound leaf the expression reads by its own expression, recursively, so the result reads only constants. The shadow's x stays #sq.x + 100; a chain like meter reading ← fiber output ← laser output ← laser power collapses to one formula over the laser's power.
  5. The free leaves are the constants the inlined formula reads that no producer drives (65–72). One free leaf and a linear formula gives a Linear handle. Several free leaves, but linear in exactly one, also gives Linear on that one: the fiber's length and loss sit inside an exponent, so dragging the meter's reading moves the laser's power and holds the rest (79–89, from Part 9).

linear is a small symbolic differentiator: it returns (a, b) such that the expression is a·var + b, or None if it isn't linear:

It's symbolic on purpose. A function that happens to look straight over the range you sampled (a sin near zero) is still rejected, so a drag never lands somewhere other than where the pointer is.

3.4Previews, and commit

A gesture is a set of previewed leaves sitting in the graph's overlay (F3.5). Stage A added the handle-aware entry point:

preview_target is what every tool calls: the select tool's move, resize and rotate (Part 7), the pen's point drags, the inspector's fields (Part 7) and the meter gauge (Part 9). Each preview also re-solves constraint clusters (Part 4) and the physics network (Part 9), so everything downstream is live while the pointer moves.

On release the overlay becomes one transaction:

Only drivers are written, meaning leaves a tool previewed on purpose. Leaves the solver moved in response are not written here; the solver reproduces them when the transaction applies (Part 4). A gesture that changed nothing (a click) produces no transaction at all, so a click never shows up in history as a "move".

3.5The drag API

Dragging a whole node is more than previewing two numbers: the pointer is in world space, the node's x/y are in its parent's space, the grab point is somewhere inside the node, and the node may be part of a constraint cluster. The store wraps all of that:

begin_drag decides once, at the grab, which of three modes applies:

  • Cluster (281–291): the node is held by constraints, so the drag places a finger (a target for the grab point) and the solver moves everything (Part 4).
  • Axes: each of x and y has its own handle. A locked axis holds still for the whole drag, with the reason logged once, rather than moving and snapping back.
  • Locked: neither axis can move.

begin_drag also adds the node to the running gesture's watched set (watch), which is what lets a later edit to it cancel the drag (Part 13). drag_to in axes mode (319–338) undoes the parent's transform, then the node's own rotation and scale applied to the grab point, to find the origin that puts the grab point under the pointer, and previews that through each free axis's handle.

3.6Same-frame reconcile

The document sync runs at the start of the frame, in PreUpdate. Tools preview in PostUpdate. Without something more, every previewed value would reach the screen one frame behind the pointer. reconcile_gesture is the in-frame half:

It drains whatever the previews changed (the dragged leaves and every binding that read them) and rewrites just that draw data, and any entities. It is scheduled right after the tools, with an ApplyDeferred so its entity commands land before anything later in the frame reads them:

The "before propagation" ordering dates from when 2D entities carried transforms Bevy propagated. Now it matters for 3D (a dragged mesh's pose) and for ordering: prepare_spatial and the 2D layer, which run after propagation, see this frame's preview. Part 11 has the whole schedule.

Rough edge

A linear handle needs a single free source. A rect bound to the sum of two sliders is locked, with the reason "bound to 2 free leaves". The roadmap's answer is a constraint cluster (Part 4) or a disambiguation policy (prefer the most recently touched source); neither exists for plain bindings yet.
