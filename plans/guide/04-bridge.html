    Into Bevy: the reconciler and writeback

    The store from Parts 2 and 3 knows nothing about Bevy. This part covers the code in between. It turns document nodes into entities, redraws only what changed, turns a drag back into one transaction, and connects undo, save and load to the Svelte shell. This is plan steps 2–4, the commits “undo redo” and “working save/load”.

    One practical point: a Bevy Entity id is recycled after despawn, so it can't serve as a node's identity. That alone rules out making Bevy the authority, and it's the first reason vision doc 04 §5.1 gives.

    4.2Two simple bridges, and why neither was chosen

    The simple version A

    Rebuild every frame. Despawn everything and respawn from the document each frame. It's always correct, but you pay for the whole scene every frame, entity ids churn (breaking selection and hover), and a drag's in-progress Transform would be overwritten.

    The simple version B

    Diff every frame. Compare every node against its entity and patch the differences. It's correct and cheaper, but it still touches every node every frame, and it has no idea why something changed.

    What was built

    Reconcile from the log. After each batch of transactions, read the new entries in the history log, collect the node ids their ops touched, and re-examine only those nodes. A frame with no transactions does no work at all. Every entity carries a Provenance(NodeId) component, and a NodeMap resource maps both ways.

    4.4sync_document: the heart of the bridge

    This is the longest function in the bridge and the one to understand first. It runs once per frame in PreUpdate. The parameter list (lines 169–181) is the list of resources above plus Commands and the clock. Here it is in three pieces.

    First: skip, or load

    The early return (182–190) is why an idle frame costs nothing: no queued work, no pending value changes, and the document's version equals the one already synced. A load tears down every entity rather than diffing, because in a different document the same id may be a different type. It then installs a fresh Store, which starts with empty history, and marks every live node as affected.

    Then: drain the queues, in order

    Transactions first, then gesture commits, then undo/redo. Errors are logged as warnings, and a rejected transaction simply doesn't happen. ts == 0 means “stamp me with the frame clock” (211–214), which is how Bevy systems submit transactions without needing a clock.

    Finally: find what changed and reconcile it

    Line 250 is the design decision from 4.2 in code. It doesn't look at what was queued; it looks at everything the log gained since SyncedVersion. That covers the queued transactions, undo and redo, and also transactions applied by other routes: the model surface calls Store::apply synchronously through the FFI (Part 7), and the sync picks those up here on the next frame without being told about them.

    For each new transaction, collect_ids reads the node ids off both the ops and the inverse:

    Why the inverse too? For a Reparent, the op names the new parent and the inverse names the old one. Both parents' child lists changed, and both need looking at. Links are skipped because a relation doesn't change any entity by itself.

    After that come the changes the reactive graph reports (259–261), such as “the bar's height is now 240 because the slider moved”. Part 5 explains where those come from; for now they are simply more affected nodes. If the version moved, the shell is told (266–268). Then the affected set goes to the reconciler.

    4.5The reconciler: node → entity

    For each affected id there are four cases (86–106): the node is live but has no entity, so spawn one; there's an entity but no live node, so despawn it; both exist, so rewrite the entity's values; neither exists, so do nothing. Parent links are set in a second pass (108–120), because during the first pass a child may be spawned before its parent.

    write_values is where document components become Bevy components, one arm per node type:

    The important detail is how it reads values. It doesn't use doc.leaf(...), the authored slot. It goes through Reader, which calls store.resolved(...):

    resolved returns the value a reader should see right now: a gesture's preview if one is active, else a binding's computed result, else a clip's sampled value, else the authored constant. So the reconciler draws bound, previewed and animated values with no special cases, and Parts 5 and 6 plug into it without touching this file.

    Note also the coordinate convention in the comment on transform_2d. Document 2D space is y-down with the origin at the viewer panel's top-left, the same as SVG and kurbo, so the entity's Transform holds document coordinates as they are. The old overlay used a y-up, panel-centred space. Two tiny helpers in panels.rs convert between screen and document space:

    Drawing: one display list for all 2D nodes

    Entities with a Doc2d component (rects, circles, bars, sliders) are all drawn into one Vello display list by render_document_layer, in document preorder, so later siblings paint on top. The list is rebuilt only when something set DocumentDirty, an entity moved (a drag in progress), the panel resized, or the selection changed. Picking uses the same painter order: pick_document_2d_system maps the cursor into each node's local space through the inverse of its global transform, so rotated and scaled shapes hit-test correctly, and it uses the node's paint index as depth. This replaced the old overlay2d.rs, which had a separate hand-written layer and hit test for each kind of demo object.

    4.6Writeback: a drag becomes one op

    This was the old square drag, in full. The square's position lived in a resource, and dragging overwrote it:

    It worked, but the new position went nowhere. No log, no undo, no file, and the Svelte inspector had its own separate path for writing the same kind of state.

    What was built

    A gesture is an intent, not a mutation (vision doc 04 §5.3). While the pointer is down, the entity moves every frame so the square keeps up with the cursor: the optimistic half. On release, the difference between the entity and the document becomes one transaction. The sync applies it on the next frame, and the reconciler writes the entity from the document, landing on the same position.

    Here are the three drag systems. Deciding happens on pointer down:

    Two things are new compared with the old code. On release (47–51) the system doesn't forget the drag; it hands the entity to PendingCommit for the commit system. On press it asks the store whether each axis has a handle (62–69): if transform2d.x is bound to an expression or driven by a clip, that axis is locked for the whole drag. That is Parts 5 and 6's rule, “a derived value has no handle”, enforced before anything moves, so nothing jumps back on release.

    For each axis it skips leaves that are bound or animated (a second guard behind the lock), compares the entity's position with the authored constant, and emits a Set only if they differ. A plain click is therefore not recorded as a move (the comment at 201–202). The label uses the node's type, so the history reads “move rect” or “move mesh”.     These systems are registered in bevy_app/mod.rs with explicit ordering: drag_apply must run before transform propagation so the moved position is drawn in the same frame (mod.rs:214–234).

    Rough edge

    The comment on sync_document's registration (mod.rs:157–159) says it runs “before input collection, so a transaction queued last frame is visible to this frame's picking”. Nothing enforces that. The picking systems in bevy_app/mod.rs are ordered after pointer_collect_system but have no .before(sync_document), and newly spawned entities only appear once Commands are applied anyway. In practice it makes no visible difference, but the comment promises an ordering the code doesn't declare. A one-line .before(pick_document_2d_system) would make it true.

    4.7Undo keys, save, load and the Document panel

    The plan allows four kinds of call across the wasm boundary: apply, view, history, document. Steps 3 and 4 added three of them. Each follows the same route: a Svelte action becomes a message, worker.ts calls a #[wasm_bindgen] function, and that function either reads the store directly or queues a request for the sync.

    Undo: the shell decides, Rust obeys

    Which keystroke means undo is a chrome decision, so it's made on the main thread (and ignored while you're typing in a text field). Only the command crosses: the message {ty: 'undo'}. The worker calls glue.undo(handle), which lands here:

    It doesn't undo on the spot. It queues a HistoryOp, and the next sync_document runs Store::undo and reconciles, as in section 4.4. The remaining_frames = 10 line (551–553) asks the frame loop to keep ticking, since the app stops rendering when idle.

    Save, load, view

    Save and view read the store directly and return a string. Load validates immediately (line 399 runs serial::load from Part 3), so a broken file is an error to the caller and never reaches the running scene. A valid one is parked in PendingLoad, and the next sync swaps it in.

    On the TypeScript side, DocumentClient wraps these messages in promises. Each request carries a requestId, and the reply with the same id resolves the promise. When the store's version changes, the sync calls send_document_changed_from_worker, the worker posts documentChanged, and the client re-reads its view, which is how the Document panel stays current:

    The same client exposes window.__iron.save / load / view / edit / ask. The smoke test drives the app through these, and you can use them from the browser console. The panel itself is Controls.svelte: Save and Load buttons, a fidelity dropdown, the live view, and the model's Ask box (Part 7).

    What was removed

    The remote inspector crate, ffi_inspector_bridge.rs, type_registry.rs, system_state.svelte.ts and the inspector's TypeScript types were all deleted in a383b89. The inspector's write half (inspector_update_component and friends) edited Bevy components directly, which is exactly the route this design closes: an edit that skips the op path has no undo and no log, and gets overwritten by the next reconcile. The plan retired it and replaced its read half with the Document panel's tree view.

    4.8The starting scene is a transaction

    The app no longer spawns demo objects in setup systems. demo.rs builds one TransactionInput labelled “open demo scene” and queues it at startup, so the demo scene can be undone, saved and viewed like anything else.

    Reading the Rust

    Lines 22–30 set up two small generators with closures. next_ids(29) reserves 29 ids up front (one per node the scene creates) and turns them into an iterator. let mut next = move || ids.next().expect("reserved") is a closure that takes ownership of that iterator (move) and returns the next id each time it's called. order works the same way over order keys, returning a0, then a1, then a2. Each Op::Create below then just says id: next() and order: order().

    The components are built by starting from Default and overwriting fields, as in let mut t = Transform2d::default(); t.x = n(500.0);, then converted with .wrap() into the Component enum from Part 2.

    The rest of the file creates the 20 random rects (with a deterministic xorshift generator, so every run looks the same), the square, the circle, the slider and bar (Part 5), the torus, and the timeline with two clips (Part 6).

    4.9How the model checked its work

    In the same commit as the bridge, the model wrote the run-iron skill (.claude/skills/run-iron/). build.sh builds the WebGL2 wasm, serve.sh runs Vite, and drive.ts is a Playwright script that reads commands from stdin (ddrag, key Meta+z, eval, shot, logs) against headless Chrome. smoke.txt works through the plan's exit criteria in order: drag the square and the torus, undo both, redo one, scrub the slider, scrub the timeline, apply a model edit, and round-trip save/load, checking the bytes match. Every screenshot in this guide comes from that script's last run.

    Before you go on
    • Changes are queued (PendingTransactions, HistoryRequests, PendingLoad, GestureRequests) and applied by sync_document at the start of the next frame.
    • The sync reconciles from the log, reading ids from ops and inverses, so anything that applied a transaction by any route gets drawn.
    • The reconciler reads resolved values, so bindings, previews and clips all render with no special handling.
    • A drag moves the entity optimistically and writes one transaction on release. Bound or animated axes are locked.
