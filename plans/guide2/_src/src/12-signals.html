Runtime signals and producers

F3 described a stack of layers that every read goes through: overlay, binding, physics, clips, constant. Two of those were special-purpose maps, and a planned simulation would have added a third special-purpose map. Phase 4 of vision 10 (50b36f1) replaced them with one runtime layer of signals, each owned by a producer. Clips and the port network became the first two producers. A Bevy system became the first host producer: 160 gas particles that have no document nodes, push on a piston, and publish a pressure the document's bindings read like any value. This part covers the layer, the publish algorithm, freezing, and the demo.

12.1One map per source doesn't scale

How it was

A map per source. The graph held animated: Leaf → Value for clips and physics: Leaf → Value for the network, and read_with checked each in turn. Each new source meant a new map, a new branch in the read order, a new case in handle ("locked because…"), and a new rule for what happens when two sources claim the same leaf. A Bevy simulation or a Model session would each have needed one.

What was built

One map of Signals, each tagged with who published it. A producer replaces its whole set of values each time it publishes. A leaf claimed by two producers keeps the first claim and reports the second. A bound leaf can't be driven at all. Bindings read a signal exactly as they read a constant, and nothing in the layer is ever saved.

12.3Publishing: replace your whole set

A producer publishes everything it holds, every time. The graph diffs that against what it held last time:

  1. Bound leaves are refused (141–144): a formula wins, and the attempt is recorded in signal_errors.
  2. The first claim wins (146–149): a leaf held by a different producer stays with it, and the newcomer gets an error. A leaf the producer re-publishes with the same value is restamped but not reported as changed.
  3. What it stopped naming is released (161–166): the difference between last time's held set and this time's.
  4. Only moved values propagate (175–183): each changed leaf is noted, unless a gesture is previewing it, and its dependents are invalidated in height order, as for a constant that was set.

A host publish isn't an isolated write. Lines 675–678 re-solve every constraint cluster live and then the network, so a signal that feeds a cluster's input moves the mechanism in the same call, and a signal that feeds a network parameter moves its solution. This is the "one evaluator" of Part 10 in practice: producers supply inputs, and the store propagates them through bindings, clusters and the network in one place.

The network is also a producer that reads its own last output: its initial guess for each unknown is the signal it published last time (x0 in resolve_physics), so successive solves start warm.

Layout is built-in producer 2

Store::resolve_physics now solves the network and then layout. layout::compute builds a Taffy tree from groups and tables, measures text, and publishes item positions and the sizes layout chooses under ProducerId::LAYOUT. It reads beneath its own previous output to avoid feeding yesterday's layout back as authored input. These published leaves are locked for ordinary direct manipulation.

Layout recomputes after transactions and relevant previews/signals; reordering previews change the flow without changing authored order. Declared transitions interpolate those derived placements as motion advances. Host producer ids now begin at 3; gas and Stats use that registry. Their runtime values remain outside saves and history.

Free running is per composition

Run mode Auto follows visible live sources and bubbles through embeds; Always forces continuous frames; On demand stops continuous updates. Gas and Stats register live sources. The settings menu and __iron.runMode edit that policy through transactions. The old Bevy UI FPS overlay has been replaced by the session's Stats composition: ordinary text nodes fed by a producer. Set it to On demand before an idle-render experiment.

12.6The piston demo

A 3D composition cylinder holds a translucent chamber (a unit cylinder scaled to radius 0.6, length 3, along X), a piston disc, and a rod. A 2D composition piston embeds the 3D view next to a stroke slider and two gauge bars. The document side is ordinary bindings:

piston.transform3d.pos = [1, 0, 0] * (1.3 - stroke.slider.value * 2.2) + [0, 1.2, 0] rod.transform3d.pos = piston.transform3d.pos + [0.9, 0, 0] pressure_bar.size.w = clamp(pressure.port.signal * 50, 0, 300) pv_bar.size.w = clamp(pressure.port.signal * (2.74 - 2.2 * stroke.slider.value) * 100 / 3, 0, 300)

Nothing in the document computes pressure.port.signal. A Bevy system does:

Three details from that excerpt. The targets are found by name and cached per document version (160–163), so an edit elsewhere doesn't re-search every frame. The producer runs only while some panel or embed shows the cylinder composition (176–190), so a hidden demo costs nothing. And it runs before sync_document: the publish's changes are drained by the sync right after it and reach the screen this frame, together with everything else.

The physics check: compressing the gas with the slider raises the pressure bar, and the P·V bar (pressure × gas length) stays level. That's Boyle's law, and it holds only if the gas really is isothermal, which elastic walls guarantee. __iron.signals() lists producers, signals and conflicts; __iron.producer('gas', 'freeze' | 'stop' | 'run') drives it.

Rough edges and open questions

Host controls remain specific. Gas and Stats publish runtime signals, but the debug document_producer control still handles gas explicitly; it is not a general simulation-service lifecycle API.

No collisions with document shapes yet. The "Live + simulating" mode (Part 10), a physics engine acting on Live document entities and publishing their poses, isn't built. The publish it would use is the one shown here.

Within one producer, nothing is checked. Two clips aimed at one leaf both go into the clips producer's single map, and the later one silently wins (F3's rough edge still holds). Conflict detection is only between producers.

Open (vision 10 §8). Q1: does the kinematic simulation of CS §11 run in iron_solve or as a Bevy producer? Q4: should the model's view of a leaf name the producer behind its value?

Before you go on
  • Reads go overlay → binding → runtime signal → constant. Clips (0), the network (1) layout (2) and host systems (3+) are all producers of the one runtime layer.
  • A producer publishes its whole set each time; the graph releases what it dropped, refuses bound leaves and other producers' leaves, and propagates only values that moved.
  • A published leaf is Locked to gestures, naming its producer. freeze turns a producer's values into one undoable transaction.
  • The gas reads Iron's poses, keeps 160 particles with no document nodes, and publishes one number before the sync, so the document stays the only thing that's saved or undone.
