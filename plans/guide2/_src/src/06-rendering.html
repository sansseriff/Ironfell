Every view is a texture

Embedding needed one thing the renderer couldn't do: draw a composition into something other than the window. Fixing that turned into a rewrite of how everything reaches the screen. Every view (a 2D panel, a 3D camera, a 3D view inside a 2D composition, a 2D composition on a plane in 3D) now renders into its own texture, sized to where it's seen, and only when something it shows changed. This part follows plans/view-textures.md: the problem, the model, the three uses, render on demand, and the two latency fixes at the end.

6.1The problem, from the source

How it was

Every camera paid for the whole window, every frame. Bevy allocates each camera's colour and depth buffers at the size of its render target, the window, and a viewport only restricts where it draws. A 3D panel a fifth of the window paid for full-window buffers; at 5K, 5120×2880 each. The 2D side merged every layer into one window-sized Vello scene, cleared and redrawn each frame. So GPU cost scaled with window area times panel count, an idle frame wasn't free, and a composition couldn't be drawn into anything but the shared screen.

The model

A view is one source seen one way, rendered into its own texture. The texture is sized to the view's footprint on screen, kept between frames, and re-rendered only when something it shows changed. A texture has three possible uses: pasted 1:1 into a panel by the window's one camera, drawn inside a 2D view under an affine transform, or sampled on a plane in 3D.

The plan's own summary of why this also enables everything else in Parts 5 and 9: once each view has a texture, "show this composition inside that one" is "draw that texture there".

6.2Vector views

A 2D layer is an entity with a DisplayList (the renderer-independent list of fills and strokes from guide 1) and a VectorLayer. The change is one field: which view the layer renders into.

Each 2D composition panel spawns one entity that is both a layer and a VectorView over the panel's rectangle (render.rs:37). Other layers can target the same view by entity: Part 7's select overlay draws into the panel's view at a higher order, so redrawing the selection box never re-encodes the document's layer.

Two encodings arrive. Vello writes premultiplied, sRGB-encoded bytes into a UNORM texture; a Bevy camera writes straight alpha into an sRGB texture. The material's mode tells the shader which it's reading, so neither gets its colours shifted.

6.33D views

A 3D panel's camera renders into its own texture instead of the window, with the same bucketing and the same retention. ViewImage tracks the texture and when the camera needs to run:

sync_view_images marks a camera active only when something it shows changed: its rectangle, its pose or lens, or any 3D content on its render layers moving, highlighting, appearing or disappearing. Otherwise it sleeps and its texture is reused. Two practical details from getting this right: a camera woken for one frame can render with stale per-view state (lights, visibility), so it stays awake for a few frames after a change; and the system runs before Bevy's frustum and visibility systems, so a camera woken this frame is culled and lit as an active view this frame.

Camera orders (Bevy needs them unique) come from the lowest free slot, so cameras appearing and disappearing never collide (scene3d.rs:272).

3D inside 2D

A 3D embed's camera renders into a texture sized to the embed's on-screen size (Part 5's EmbedView), and the 2D view that contains the embed draws that texture with DrawCmd::Texture, under the embed's whole transform, in painter order. So a 3D view inside a 2D composition can be rotated, scaled, clipped and drawn over like any other shape. Vello can't read a Bevy camera's sRGB texture directly, so each one is converted into Vello's encoding first (Convert, hybrid.rs:937).

Picking goes the other way: PointerToCamera stores the map from window pixels to the embed camera's own texture pixels, through every transform on the way, so clicking the torus inside a rotated embed casts the ray from the right place.

2D on a plane in 3D

A 2D composition embedded in 3D is a plane mesh whose material samples an offscreen vector view: a VectorView marked Offscreen, rendered but never pasted into the window. Its resolution comes from how large the plane appears: project the plane's corners through every camera that sees it, and take the largest screen-space length of one document pixel:

Densities step by powers of √2, so a slow camera dolly changes the texture size rarely. This is the first piece of the user's "tiled, demand-driven textures" extension (plan §4): views are already described as a content-space region at a density, and demand is already computed per use. The tiles themselves are future work.

6.4Render on demand

With every view retaining its texture, a frame where nothing visible changed needs no GPU work at all. WorkerApp::frame runs the main world, asks whether anything the window shows changed, and only then runs extraction and rendering:

"Changed" covers display lists, views, active texture cameras, UI text, panel layout and asset events. A change keeps rendering for three more frames (linger), since per-view state settles over a frame or two. Two things had to stop changing every frame for this to pay off: the camera controller wrote its transform every frame even at rest, and the FPS text updated every frame; both were fixed. The FPS overlay now updates four times a second.

6.5Two latency fixes

After the migration you reported more lag on your display. Headless pacing was a steady 16.7 ms in every case, so the report wasn't reproduced, but reading the schedule turned up two real one-frame delays:

  1. 2D could reach the window a frame late. Vello's render_scene and Bevy's render_system (which runs every camera and composites the window) were in the same render phase with no order between them. If Vello ran second, the window pasted last frame's 2D. Now Vello is ordered first (line 147).
  2. 3D inside 2D was a frame behind its camera. The 2D view sampled the 3D texture before Bevy had rendered this frame's image. Views that draw a 3D texture now render inside the window camera's own schedule, after every 3D camera and before the composite, in the same GPU submission (150–156). Each such view has its own Vello renderer, because a renderer's queued buffer writes all land before the submission, and two views sharing one would overwrite each other.
Rough edges

The window still pays one full-window composite pass on any frame that renders; a custom final pass that pastes only changed rectangles is the next lever if it ever shows in a profile. Plane textures have no mipmaps yet, so a plane seen at a glancing angle shimmers. Tonemapping shifts plane colours slightly, since the card is lit like any surface. None of the tiled-texture extension (plan §4) exists beyond the foundation described above.
