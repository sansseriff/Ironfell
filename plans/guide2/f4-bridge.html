    Bevy and the model

    The store from F1–F3 knows nothing about Bevy, the browser or Claude. This page covers the three ways it meets the outside: the bridge that turns document nodes into Bevy entities and redraws only what changed; the wasm boundary the Svelte shell talks through; and the model surface, where Claude reads a view and writes an edit that becomes an ordinary transaction.

    You needF2 (transactions, the log, Store::apply) and F3 (resolved values, drain_changes, previews).
    Filessrc/document_bridge/{mod,materialize,demo}.rs, src/engine_api.rs (with thin hosts in web_ffi.rs and src-native/), src-ui/worker.ts, src-ui/model/{agent,edit,schema,manifest,transport}.ts.

    F4.1Bevy words used here

    WordMeaning
    EntityAn id for "a thing in the scene", with no data of its own. Recycled after despawn, so it can't be a node's identity.
    Component (Bevy's)Data attached to an entity: Transform, Mesh3d. Not the same as a document component.
    ResourceA single global value in the Bevy world: DocumentStore, NodeMap.
    SystemA function Bevy calls each frame. Its parameters declare what it reads and writes.
    Res<T> / ResMut<T>Read / write access to a resource, as a system parameter.
    Query<(&A, &B)>"All entities that have A and B."
    CommandsA queue of spawns, despawns and inserts, applied a little later in the frame.
    PreUpdate, Update, PostUpdateSchedules that run in that order every frame.

    F4.2Two simple bridges, and the one built

    The simple version A

    Rebuild every frame. Despawn everything, respawn from the document. Always correct, but you pay for the whole scene every frame, and entity ids churn, breaking selection and hover.

    The simple version B

    Diff every frame. Compare each node with its entity and patch differences. Cheaper, but it still touches every node every frame and has no idea why anything changed.

    What was built

    Reconcile from the log. After each batch of transactions, read the new entries in the history log, collect the node ids their ops touched, and re-examine only those. Add the nodes whose resolved values moved (bindings, previews, signals). A frame with nothing new does no work. For each touched node the reconciler rewrites its draw data, and its entity if it has one. Since October 17 most 2D nodes don't: draw data lives by NodeId, and entities exist only for 3D nodes and the working set (Part 10). Every entity carries Provenance(NodeId), and NodeMap maps both ways.

    The pattern throughout: anything that wants to change the document pushes a request into a queue, and one system, sync_document, drains every queue in a fixed order early in each frame. Part 11 lists the exceptions (host calls that apply immediately) and shows the whole frame.

    F4.4sync_document: the heart of the bridge

    It runs once per frame in PreUpdate, right after any producer has published. In three pieces:

    Skip, or load

    The early return is why an idle frame costs nothing: no queued work, no pending value changes, and the version equals the one already synced. A load tears down every entity and all draw data rather than diffing (the same id may be a different type in the new document) and installs a fresh Store with empty history.

    Drain the queues, in order

    Transactions, then gesture commits, then undo and redo. A rejected transaction is logged and simply doesn't happen. ts == 0 means "stamp me with the frame clock". CommitMerged commits and then folds the commit into the duplicate before it, so an Alt-drag is one undo step (Part 13).

    Read the log, then reconcile

    Line 388 is the design decision in code. It doesn't look at what was queued; it reads everything the log gained since SyncedVersion. That covers queued transactions, undo and redo, and also transactions applied by other routes: the model surface calls Store::apply synchronously through the host boundary, and the sync picks those up here without being told. For each, it collects ids from the ops, the solver's derived ops and the inverse (408–410):

    Why the inverse too? For a Reparent, the op names the new parent and the inverse the old one; both child lists changed. Then come the nodes whose resolved values moved (415–417), such as a bar whose height binding re-evaluated or a gauge a producer just published. If the version moved, a DocumentChanged event is pushed for the shell (421–424), which is how HTML views refresh. Then the affected set goes to the reconciler (433).

    F4.5The reconciler: node → draw data, and an entity where one is due

    First (340–353), a touched point or contour adds its enclosing path, since points have no draw data of their own (Part 7). Then, for each affected id, four cases: live with no entity, write its draw data and spawn an entity only if Modes says one is due; entity with no live node, despawn it; both, rewrite; neither, drop any draw data. Nothing under a library is drawn (Part 2). A second pass, shown in Part 10, places 3D descendants, because entities are flat.

    write_values turns document components into draw data and Bevy components, one arm per node type, and reads every value through Reader:

    It calls store.resolved(…), not doc.leaf(…): the value a reader should see now, through every layer of F3. So the reconciler draws bound, previewed, animated, published and solved values with no special cases. Document 2D space is y-down with the origin at the top-left, as in SVG. A 2D node's draw data is in its own local space, and its placement comes from the store (Part 10); each panel's pan and zoom are applied when drawing (Part 5).

    Where gestures fit in the frame

    sync_document runs at the start of the frame. Tools run in PostUpdate, where a drag previews into the store (F3.5). Without help, every preview would reach the screen a frame late, so a second, smaller pass, reconcile_gesture, drains the preview's changes and rewrites that draw data in the same frame. Part 3 covers it; Part 11 places it in the whole schedule. On release, the tool pushes a GestureRequest::Commit, and the next frame's sync turns the previews into one transaction.

    The starting scene is a transaction

    The app spawns nothing by hand. demo_scene builds one TransactionInput and queues it at startup, so the demo is saved, viewed and undone like anything else. Lines 23–31 set up two generators: next_ids(61) reserves ids up front and next hands them out; order hands out a0, a1, a2…. The rest of the file (now long) builds the compositions, the pendulum, the bar definition, the optics and thermal chains, the timeline, and since October 17 the piston demo. Parts 2–12 show its pieces.

    F4.6The host boundary

    On the web the app runs in a web worker: Bevy, the store and the model surface's TypeScript together. The Svelte shell on the main thread sends messages; worker.ts calls #[wasm_bindgen] functions in web_ffi.rs. Since the macOS target (Part 11), those are thin wrappers: the behaviour lives in engine_api.rs, shared by both hosts, and each function either reads the store directly, applies to it, or queues a request for a system.

    Which keystroke means undo is chrome policy, decided on the main thread (and ignored while you type in a text field); only the command crosses. It is queued with the other tool keys, so it keeps its place relative to a Delete pressed just before it (Part 11 shows the bug this fixed); remaining_frames keeps the frame loop ticking, since the app stops rendering when idle (Part 6). Save and view read the store directly and return strings. Load validates on the spot, so a broken file is an error to the caller and never reaches the scene:

    One call is different. The model needs every error in one round trip, so document_apply applies now and answers in JSON instead of queueing:

    expect_version is compare-and-swap. The model read <document version="7">; if you dragged something while it was thinking, the document is at 8 and its edit, based on a stale view, is refused with "re-read before retrying". If you are dragging while it applies, the edit is classified against your gesture (Part 13). On success the bridge still picks the transaction up from the log on the next frame.

    The other calls the model surface uses keep the store in charge of what only it should decide: document_next_ids and document_next_relation_ids (ids come from the store's counter), document_place (order keys, F1.8), and document_schema (the registry as JSON, F1.6). On the web they reach Rust as documentCall messages, decoded by name through engine_dispatch's allowlist. Later parts add more: link, inspect, selection, signals, export_svg; the field guide lists them.

    F4.7The model surface

    The simple version A

    Hand it the file, take back a new file, and diff. The model must reproduce everything it didn't mean to change; ids get lost or invented; one hallucinated line corrupts the scene.

    The simple version B

    One tool call per op, with JSON schemas. Precise but verbose: raw order keys, fully qualified paths, many round trips with no atomicity between them.

    What was built: read markup, write ops

    The model reads views (F2.9) and replies with one <edit> block of declarative verbs, each naming its target by id:

    <edit expect-version="7">
  <set id="#N" color="#ff0000"/>
  <create id="$n" type="rect" parent="#1" x="300" y="120" w="{= #O.slider.value * 100}" h="40"/>
</edit>

    TypeScript turns that into one transaction: it resolves $n to a real id, asks Rust for order keys, maps w to size.w and color to fill.color, coerces #ff0000 to a colour, turns {= …} into a binding, and applies it with the version check.

    It runs in the worker, next to the wasm, so every question it asks the store is a plain synchronous call; only the network call to Claude is asynchronous. One turn:

    Build the system prompt from the schema, and the user message from the model view, the tree view, the current selection (Part 8) and the request (22–34). Call the model. Pull out the <edit>. Apply it with the label "model: …". If it failed, send back the failure and ask for one corrected edit. At most two attempts. The actor is model, so the edit sits on the same undo stack as your drags, and Cmd+Z undoes it.

    The edit parser: four passes, one transaction

    1. Collect verbs in order, rejecting unknown ones with the list of valid ones.
    2. Mint aliases. Every <create id="$something"> gets a real id from the store, so later verbs can say parent="$group". The model never invents a real id.
    3. Batch placements by (parent, after), one place call per group, so two creates "at the end of #1" get two distinct keys in order.
    4. Build ops in exactly the JSON shape Rust's Op deserialises (F2.2).

    Attribute names and values are both resolved from the schema, so they can't disagree with the validator:

    A bare field name resolves to the first component, in the type's declared order, that has it: on a rect color is fill.color, and stroke.color must be written in full. coerce is forgiving about format ("12", 12px; #rrggbb or rgba(…); 9.58 mW for a quantity) and strict about meaning.

    Parse errors and store errors come back the same way, as markup the model reads just as it read the view:

    Successful edits that moved constrained nodes also come back with an <applied> summary naming what the solver did (Part 4). The system prompt (manifest.ts) is generated from document_schema() at run time, so the vocabulary the model is told and the vocabulary the validator enforces can't drift. The transport (transport.ts) calls the Claude API from the browser with your key, stored in this browser's local storage; it's a local tool, not something to deploy.

    Before you go on, and the whole of Foundations in five lines
    • The document (iron_document) holds all authored state: stable ids, typed components, slots, relations. Its writes are private to the op applier.
    • Every change is a transaction of ops that commits entirely or not at all and records its own inverse. Undo is another transaction.
    • The reactive graph layers previews, bindings and runtime signals over the constants; every reader, including the reconciler, sees the same resolved values.
    • The bridge reconciles from the transaction log, whoever applied the transaction, writing draw data by node and entities only where Bevy acts. Gestures preview each frame and commit once.
    • The model reads views and writes <edit> markup, which becomes an ordinary transaction with a version check. Part 1 picks up from here.
