    Gestures have owners

    Part 3's gestures were a store-wide overlay of previews plus one commit on release. That was safe only while nothing else wrote the document during a drag. Since the model applies edits between frames, the inspector writes immediately, and undo can arrive mid-drag, other things do. Commit ac92fa7 gave each gesture an identity and a set of watched nodes, and made every other transaction be classified against it first. This part covers the three leaks that forced it (one of them inside the constraint solver), the algorithm in Store::apply, how tools find out, Alt-drag as one undo step, copy and paste, and the pointer state machine that now drives every edit.

    You needF2 (apply, run, history), F3.5 (the overlay), Part 3 (handles, begin_drag), Part 4 (clusters, fingers, solve-on-apply).

    13.2What a gesture is now

    Next to those, the store keeps the fields a gesture is made of. drivers is the set of leaves the tool previewed on purpose (what a commit writes); fingers are the drag grips the solver satisfies; ended remembers how the last gesture finished, so its tool can ask afterwards.

    13.3The classification in Store::apply

    Four steps, in this order for reasons:

    1. Classify before applying (962). conflict asks "is a watched node, or an ancestor of one, deleted?" against the document before the delete, while is_ancestor can still answer.
    2. Suspend (963): take the driven overlay values, drivers and fingers into a Suspended record and clear the overlay, so the transaction runs and solves against the document alone.
    3. Apply: the ordinary path of F2: run on a clone, swap, after_transaction, solve-on-apply.
    4. Decide (966–973): a classified conflict, but only if the transaction actually applied, or the solver having moved a watched node (moved scans derived_ops), ends the gesture with that reason. Otherwise the previews go back on top of the new document and clusters re-solve live with the finger.

    Resume checks that each leaf still exists (602) before re-previewing it. What counts as a conflict:

    The other transaction…VerdictExample
    deletes or reparents a watched node or an ancestorcancelthe model deletes the group you're dragging a child of
    sets a leaf the gesture drivescancelthe model sets the slider you're scrubbing
    sets a GEOMETRY leaf of a watched node, or binds any of its leavescancelthe model moves the square you're dragging
    adds or removes a geometry component on onecancela corners component appears
    links or unlinks a constraint or clip to onecancela distance constraint now holds it
    makes the solver move a watched nodecancelthe model drags the pendulum's platform while you hold the ball
    anything elsecarry ona colour, a name, another node's position

    GEOMETRY (gesture.rs:73) lists the components a gesture reads to turn the pointer into values: transforms, size, radius, corners, arc, handles, path shape, contour, frame, group clip, slider. A colour isn't one, so recolouring the node you're dragging doesn't stop the drag.

    Undo and redo always cancel a running gesture first (Store::undo, lib.rs:1049), so Cmd+Z mid-drag takes the drag back rather than undoing something underneath it.

    13.4How the tool finds out

    The store can't call the tool. The tool keeps the id of the gesture it owns and asks each frame:

    Once cancelled, the overlay, drivers and fingers are already gone, so even a commit request would find nothing to write. The tool goes idle, its release does nothing, and the model's edit stands. The inspector's number scrubbing uses the same contract over the host boundary: inspect_scrub("begin") returns the gesture id as a token, and every "move" checks active_gesture() == token before previewing (engine_api.rs:764). One-off inspector edits go through Store::set_through_handle: a normal transaction through the leaf's handle, outside the overlay, classified like any other.

    Commit can now add components

    Dragging a rect's corner-radius dot previews corners.tl on a rect that has no corners component. handle answers Direct for a leaf of a component the type allows but the node lacks, and the commit prepends an AddComp with defaults plus the previewed fields (684–698, 714–715). So "round this corner" is one transaction.

    13.6Copy and paste: a fragment and its closure

    There is no copy op. Copying computes a closure (the roots, their descendants, and what belongs with them though nobody selected it) into a Fragment: a small document holding the nodes under their original ids. Pasting turns it into Create and Link ops with fresh ids, one transaction. The interesting part is what happens to each reference that leaves the copied set:

    ReferenceRule
    figures (shape → entity)the entity is copied too, with its ports and equations: a copied laser is a second laser
    connectioncopied when both ports are; otherwise the copy's port is unconnected
    constraint, clipcopied when every operand or target is
    binding reading an outside leafkept within the same document; frozen to the value it read when pasted elsewhere
    instance.def, embed.source, camerakept: definitions and compositions are shared
    selects (session)never copied

    "Same document" is decided by DocumentOrigin, a random token renewed whenever a document is loaded and stamped into every fragment. A paste in the same tab and session keeps references to outside nodes; one from another tab or an earlier document freezes them. The fragment's text form is the canonical file format with paste metadata, so it survives the system clipboard and migrates like an old file. A paste into a different container keeps the copy where it was on screen, by composing world affines (a_paste_into_another_container_keeps_its_place_on_screen).

    Rough edges

    merge_with_previous only folds when the duplicate is still directly below the move in past. If anything else lands in between (a model edit mid-Alt-drag), the move stays a separate undo step, and retract refuses with "the copies stay". Selection changes still aren't in undo (Part 8).

    Before you go on
    • A gesture has an id and watched nodes. Every other transaction is classified against it, applied and solved without its previews, and then either resumes it or cancels it with a reason.
    • Solving without the overlay and fingers is what stops an unrelated transaction from committing a half-finished constrained drag.
    • Tools poll gesture_status; a cancelled gesture's release writes nothing. Undo and redo cancel first.
    • Alt-drag duplicates mid-gesture (applied at once), and the duplicate and move become one undo entry; the log keeps both. Paste is one transaction of fresh ids, with rules for every reference that leaves the copied set.
