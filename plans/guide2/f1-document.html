    Foundations 1 of 4 · Document model

    What the document is made of

    Everything in Iron is stored in one place: a document held by a small Rust crate, iron_document, that knows nothing about Bevy. This page covers the data, not yet how it changes: ids, nodes, relations, values, the slots that hold them, facets, the registry of node types, sibling order and deletion. Each piece is introduced by the simple version it replaces and the specific way that version breaks.

    You needNothing. If Rust syntax gets in the way, the phrasebook at the end of this page covers the twenty or so constructs the code uses.
    Filesid.rs, value.rs, facet.rs, registry.rs, document.rs, order.rs, all in src/iron_document/src/.
    About the Foundations pages

    These four pages replace guide 1 (plans/archive/guide-spine/) for anyone starting here. They keep only what is still true of the code today, with excerpts from the current tree. Guide 1 described the system at an earlier commit and spent time on decisions that have since been overtaken: the old one-op-per-drag writeback, the Document panel, a fixed list of demo ids. You don't need any of that to read Parts 1–14.

    F1.1Start with the obvious document

    The simple version

    If you were in a hurry, the scene would be JSON with things nested inside things, keyed by name:

    { "scene": { "children": [
    { "name": "square", "type": "rect", "x": 500, "y": 420, "w": 80, "h": 80, "color": "#333" },
    { "name": "circle", "type": "circle", "x": 160, "y": 330, "r": 40 }
] } }

    Easy to write, and it works until the first real requirement arrives.

    Six things go wrong with it, and each explains a piece of the real design:

    Breaks because……which the real design answers withSection
    A name is not an identity. Rename "square" and every reference to it breaks. A model will invent names, and two things can share one.Opaque ids, never reused: NodeIdF1.2
    Nesting ties where a node is to what it is. Moving it into another group means deleting and re-inserting.A flat table of nodes, each with a parent fieldF1.3
    "x": true is accepted. "colour" (a typo) is silently kept and ignored.Typed facets, and a registry of which facets each type allowsF1.4–F1.6
    A property can only hold a value. It can't say "this is the slider's value × 300".Slot: a value or a bindingF1.4
    Children are ordered by array index. Inserting one renumbers every later sibling.Fractional order keysF1.8
    Deleting removes the node, so undo recreates it with a new identity, and anything pointing at it dangles.TombstonesF1.9

    F1.2Identity: NodeId

    An authored node's id is an opaque number that means nothing: not its position, name or type. The store hands out the next number from a counter and never hands it out again, even after deletion. For display it's written in base62 (digits, then A–Z, then a–z) with a # in front: #1, #M (22), #1a. You'll see ids like these in every view and log line.

    There are two kinds of id, node ids (#…) and relation ids (r…), which need identical code (printing, parsing, JSON). id.rs writes it once as a macro and invokes it twice:

    Reading the Rust

    macro_rules! id_type is a template. $name:ident matches an identifier such as NodeId, $prefix:literal a literal such as "#", and $(#[$m:meta])* "zero or more attributes", which is how the /// doc comment is passed through. Everything after => is pasted once per invocation with those names filled in.

    Line 122 is the point: pub struct $name(u64), with the field not pub. Code outside the crate can't read or construct the integer; only from_raw and raw, which are pub(crate), can. JSON writes the id as its string ("#M", never 22). So nothing outside the store can depend on ids being numbers. is_session belongs to Part 8: ids from 2⁴⁰ up are for state that's never saved.

    F1.3The node record, and relations

    A node holds almost nothing itself. Its properties live in separate facet tables (next section). The node is identity, type and placement:

    • parent: Option<NodeId>. None means a root. Placement is a field, not nesting, so moving a node changes this one field.
    • order: OrderKey positions the node among its siblings (F1.8).
    • tombstoned: Option<Version> records when it was deleted, if it was (F1.9).

    A relation is any link between nodes that isn't parent and child. It has its own id, a kind, and a small data map. Relations are how the later parts connect things without nesting them: a clip animates its target (F3), a figure figures an entity (Part 5), a constraint constrains its operands (Part 4), a connection connects two ports (Part 9), the session's selection selects nodes (Part 8). They're stored in their own table and indexed in both directions, so "what does this clip drive?" and "what drives this node?" are each one lookup.

    F1.4Values, and the slots that hold them

    A leaf is one editable authored value, such as "the square's x". Every leaf holds a Value of a known kind:

    Quantity and Record are Part 2's subject. ValueKind is the matching type tag, used to check that a Number field only ever receives numbers; its extra member Any is for fields that take whatever kind their target has (clip endpoints, port defaults).

    A leaf doesn't hold a bare Value, though. It holds a Slot, which answers the fourth problem in the table above:

    • Slot::Const(value): an authored constant. "x is 500."
    • Slot::Bound(expr): an expression over other leaves. "height is #O.slider.value * 300." The slot stores the formula, never its result. Results live in the reactive graph (F3).
    • Slot::Animated(Reserved): can never be built. Its payload contains an enum with no variants, so no value of it exists, and match r._private {} (line 442) is Rust's way of saying "this branch can't run". It was reserved for clip-driven values, which ended up as a layer in the graph instead (F3.6). Ignore it.

    In JSON the kind stays visible: numbers, bools and strings are bare, vectors are arrays, and colours, enums, refs and quantities are single-key objects ({"rgba": […]}, {"enum": "linear"}, {"ref": "#M"}, {"q": [0.01, "W"]}). A binding is {"bind": "<expression text>"}.

    F1.5Facets: typed structs from one table

    Leaves are grouped into facets, each a small named bundle: transform2d holds x, y, rot, sx, sy; fill holds color, opacity. A leaf's address is facet.field, as in transform2d.x.

    The simple version

    One map per node, HashMap<String, serde_json::Value>. Every reader checks at run time that "x" exists and is a number. Typos are silent.

    What was built

    A Rust struct per facet, one Slot field per leaf, plus a static table of field names and kinds. Readers get typed access; the validator, file loader, view renderer and the model's schema all read the same table.

    facet.rs declares every facet in one table and lets a macro generate the structs and lookups. A few entries:

    Read Radius / "radius" => Radius { rx: Number = Value::Number(50.0), ry: … } as: "a facet whose enum variant is Radius, whose JSON name is "radius", whose struct is Radius, with fields rx and ry of kind Number, each defaulting to 50." (Until schema 4 there was a circle type with one r; the loader migrates it to an ellipse with equal radii.) The table now includes additional text, layout, component, interaction and context facets, including the Figma-style appearance added on October 14–15 (corners, arc, shadow, gradient, appearance, group_clip, contour); the later parts introduce them as they come up.     $( … )* means "repeat for each match". The outer repetition matches each facet entry, the inner one each field.     The leaf address: LeafPath

    A LeafPath is a facet kind plus a field name. The field is a &'static str pointing into the generated table (or, for a dynamic field, an interned name), so a path is two small values that are free to copy. The only way to make one is LeafPath::new (or "fill.color".parse()), which rejects unknown fields. An unknown path is an error, never a silent no-op; that rule recurs all the way up to the model's edit parser.

    When a leaf also needs to say which node, it becomes a Leaf { node, path } (expr.rs:27), printed #O.slider.value: exactly the syntax expressions use.

    F1.7The Document: tables and indexes

    • The tables (lines 91–99) are the data: nodes by id, facets by kind and then by node, relations by id, the id counters and the version. This is what's saved.
    • The indexes (lines 103–108) are derived, to make questions fast: a node's children in order, the roots, nodes by type, nodes by facet, relations by source and by target. Never saved; rebuilt after loading.

    Components are stored by kind first, so "every transform2d" is one lookup and, in the saved file, all transform2d records sit together.

    Reads are public

    Everything under // ---- reads is pub and takes &self:

    leaf(id, path) is the most used: find the facet, then the field, return the Slot. The ? on line 280 means "if this node has no such facet, return None". Others you'll meet: live(id) (the node, only if not deleted), children, descendants, is_ancestor, nodes_of_type, relations_from, relations_to.

    Writes are pub(crate)

    …and below it insert_node, restore_node, tombstone, set_parent, set_order, insert_facet, remove_facet, insert_relation, remove_relation, all pub(crate).

    Every method that changes the document is pub(crate): callable only from inside iron_document. The Bevy app, the FFI and the tests can read the document but cannot write it except by submitting ops (F2). "No code path mutates the store directly" isn't a convention here; code that breaks it won't compile. check_invariants cross-checks every index against the tables, and the tests call it after every transaction.

    F1.8Sibling order without renumbering

    The simple version

    Store each child's index: 0, 1, 2, 3. Inserting between 0 and 1 renumbers every later sibling: one insert rewrites N nodes, and N nodes show as changed to undo, to Bevy and to the model.

    What was built

    Each node holds a short string key, and siblings sort by comparing keys as strings. To insert between two siblings, make a key that sorts between theirs. No other node changes.

    CallResultWhy
    OrderKey::first()a0The starting key.
    after(a0)a1Appending increments the integer part.
    between(a0, a1)a0VNo integer fits between 0 and 1, so it adds a fraction. V is base62's middle digit.
    before(a0)ZzUpper-case heads are the negative side; they sort before lower case.
    after(az)b00The integer outgrew one digit. The head letter says how long it is.

    It works because the base62 alphabet 0-9 A-Z a-z is also in ASCII order, so plain string comparison sorts keys correctly. This is the published rocicorp/fractional-indexing scheme. The rule to remember: code outside the store never computes order keys. It asks with OrderKey::first/after/before/between, or from TypeScript with document_place.     F1.9Deletion keeps the record

    Deleting a node sets tombstoned = Some(version) and removes it from every index, so children and nodes_of_type stop seeing it. The record and its facets stay, which buys three things:

    • Stale references fail loudly. An op naming a deleted id gets "#M was deleted at version 5", not "no node #M".
    • Undo restores the same id. Recreating a tombstoned id counts as a restore (F2). Anything that referred to #M refers to it again.
    • Ids are never reused. The counter only goes up.

    Relations are the exception: unlinking removes the row, and undo re-links it with the original id.

    F1.10A Rust phrasebook for this codebase

    You don't need all of Rust to read this code; about twenty constructs cover it. If an excerpt stops you, look here first.

    Shapes of data

    You'll seeIt means
    pub struct Node { pub id: NodeId, … }A record with named fields, like a TypeScript interface that is also a class.
    pub struct Version(pub u64);A tuple struct: one unnamed field, read as .0. A newtype gives a plain number its own type, so a Version can't be passed where a NodeId is expected. store.0.apply(…) reaches inside one.
    pub enum Op { Create { … }, Delete { id }, … }An enum whose variants each carry their own data, like a TypeScript discriminated union.
    #[derive(Clone, Debug, PartialEq)]"Write the obvious implementation for me": copying, printing with {:?}, comparing with ==.
    Option<T>Some(value) or None. Rust has no null.
    Result<T, E>Ok(value) or Err(error). Errors are return values, not exceptions.
    BTreeMap, BTreeSet, HashMap, Vec, VecDequeSorted map, sorted set, unsorted map, growable array, double-ended queue. The store uses the sorted ones nearly everywhere, which is why files and views come out in a stable order.
    Box<Expr>A pointer to a heap value. Needed when a type contains itself, as an expression tree does.

    Behaviour

    You'll seeIt means
    impl Document { … }The methods of a type, kept apart from its data.
    &self / &mut selfThe method reads the value / may change it. version(&self) can't change the document; apply(&mut self, …) can.
    &T, &mut T, .clone()Borrow to read, borrow to change, or make an independent copy.
    pub · pub(crate) · pub(super) · nothingVisible everywhere · inside this crate · in the parent module · in this module only.
    match x { A => …, B { id } => … }A switch that must handle every case and can pull data out of each variant. Add an op kind and the compiler points at every match that forgot it.
    trait LeafStruct { … } + impl LeafStruct for FillAn interface, and one type's implementation of it.
    fn get<T: LeafStruct>(…) -> Option<&T>A generic function. doc.get::<Timing>(id) asks for that node's Timing facet, typed.
    impl Display / impl FromStrWhat .to_string() and "…".parse() call. So "transform2d.x".parse() builds a LeafPath.

    Control flow shorthands

    You'll seeIt means
    let tx = self.run(input)?;"If this is an Err (or None), return it now; otherwise unwrap it."
    if let Some(x) = maybe { … }"If this matches, bind the inside and run the block."
    let Some(e) = thing else { return };"Unwrap this or leave the function." A guard clause; it opens most Bevy systems.
    if let A = a && let B = bSeveral matches joined with && (Rust 2024).
    |n| n.is_live(), move |…|A closure (an arrow function); move makes it own the variables it uses.
    .iter().filter(…).map(…).collect()Iterator chains, like JavaScript array methods but lazy.
    -> impl Iterator<Item = &Node>"Returns something you can loop over that yields &Node."
    .expect("declared leaf"), .unwrap()"This can't fail; if it does, crash with this message."
    Three things that look scarier than they are

    Lifetimes ('a, 'd, 'static) are the compiler's name for how long a borrowed reference stays valid. fn live<'d>(doc: &'d Document, …) -> Result<&'d Node, …> says only that the returned node points into doc. &'static str is a string baked into the program. You can read past them almost every time.

    Macros end in !: format!, vec!, write! build strings and lists; macro_rules! defines a code template, as id_type! and facets! above.

    Attributes are #[…]: #[derive(…)] generates code, #[serde(tag = "t")] tunes JSON, #[wasm_bindgen] exports a function to JavaScript, #[test] marks a test, and Bevy adds #[derive(Resource)] and #[derive(Component)].

    Before you go on
    • Nodes have opaque, never-reused ids (#M). A node record is only type, parent, order key and tombstone. Relations link nodes without nesting them.
    • Properties live in typed facets generated from one table. A leaf is facet.field and holds a Slot: a constant or a binding.
    • The registry says what each node type may hold, and is exported as JSON for the model.
    • The document's reads are pub; its writes are pub(crate), reachable only from the op applier, which is F2.
