Changing it: ops, transactions, undo

Part 2 ended with a document whose write methods can't be called from outside the crate. This part covers the one door that is open: ops, grouped into transactions. Undo falls out of that design almost for free. The part ends with the two ways data leaves the store: the saved file and the view.

3.1Why not just set the field?

The simple version

Give the document a public setter and call it: doc.set_x(square, 600.0). Or skip the setter and write the field.

Everything this project wants from the document then fails:

  • Undo needs the old value, which is gone once you've overwritten it.
  • Bevy needs to know which nodes changed, or it has to rebuild the whole scene.
  • The model sends several changes at once. If the third is invalid, the first two have already happened and the document is half-edited.
  • History can't say who changed what (a person, the model, the system) or what they meant (“move rect”, not “set x14”).

The answer, taken from vision doc 04 §3: every change is described as data first (an op), ops are grouped into a labelled transaction, and a single applier executes them. Undo, the Bevy sync and the model's invalidation all read the same log of applied transactions.

3.2The nine ops

#[serde(tag = "t", rename_all = "snake_case")] on line 17 sets the JSON shape: each op becomes an object with a "t" field naming its kind, as in {"t":"set","id":"#2","path":"transform2d.x","slot":200.0}. The TypeScript model surface builds exactly these objects in Part 7.

The central property of the design: every op has an inverse op, and the applier computes that inverse while applying, when the old state is still available.

3.3Transactions: what goes in, what gets recorded

There are two structs because the caller and the log need different things:

  • A TransactionInput is what a caller submits: a label, an Actor (Human, Model or System), a timestamp, an optional idempotency key, and the ops.
  • A Transaction is what the log keeps: everything in the input, plus the version it produced and the computed inverse.

3.4The applier: one function per op

apply_op is the dispatcher. It takes the working document, the op's position in the transaction (so errors can say “op 2”), the op itself, and the version this transaction will produce. It returns either the inverse ops or an error:

Small ops such as Reorder and Unlink are handled inline. The rest go to a helper each. set is the simplest complete one and the pattern for the others:

  1. The node must be live (line 405). live(doc, cx, id)? returns an UnknownNode or Tombstoned error, and the ? passes it straight back to the caller.
  2. A binding is validated (lines 406–408): every leaf it reads must exist, and it must not end up depending on itself. Part 5 covers this.
  3. The node must have the component (lines 409–414). ok_or_else turns “no such component” (None) into an UnknownPath error.
  4. The value is type-checked and swapped in (lines 415–417) by Component::set from Part 2, which returns the old slot.
  5. The inverse is built from that old slot (lines 418–422). No other bookkeeping is needed.

Delete: the one whose inverse needs care

Deleting a group tombstones the group and everything under it. Each tombstoned node gets its own Create in the inverse, carrying the components it had, so undo restores the same ids with the same data. Order matters: a child can't be restored under a parent that is still deleted. The loop walks the nodes deepest-first, so the inverse list ends with the group. Undo reverses the list, so the group is recreated first and its children after.

Create, and the rules about ids

Three rules about ids live here:

  • An id already in use is refused (line 269).
  • A fresh id must come from the counter (lines 273–281). Callers reserve ids with Document::next_ids and use them in Create ops. An id below the counter that isn't a tombstone is refused, so ids can't be reused.
  • A tombstoned id means “restore” (line 271 and line 291). This is how undo-of-delete gets the same node back.

The two checks it calls are short and worth knowing by name: check_parent (the parent is live and its type admits this child) and check_components (every component is allowed for this type, none is given twice, and every required one is present). reparent adds the cycle check: you can't move a node inside its own descendant.

Rough edge

The comment on apply_op (op.rs:158–159) says “on error doc is untouched: every check precedes every mutation”. That isn't quite true of create and add_comp: they insert the node or component first and run check_component_bindings afterwards (lines 305 and 446), so a node can bind to its own leaves. It is safe only because of the next section: the whole transaction runs on a copy, and a failed copy is thrown away. The comment at line 384 says so. If Store::run ever switches from cloning to rolling back through inverses (its own comment suggests that as a future optimisation), these two functions would need revisiting.

3.5All or nothing: Store::run

The model can send several ops in one transaction, and they must either all apply or none. The simplest correct approach, which is the one used here: copy the whole document, apply every op to the copy, and swap the copy in only if nothing failed.

Note that the loop doesn't stop at the first error (lines 377–382). It keeps going and collects every error, because a model fixing a rejected edit wants the whole list in one round trip, not one error per retry. The ops after a failed one run against the copy as it stands, which is good enough for reporting. Here is a real rejection:

The comment above run addresses the cost: one clone per commit, not per frame, because a drag or a slider scrub produces one transaction when it ends. That's cheap for a scene of this size and simple to reason about.

3.6Store::apply, the public entry point

Around run, apply does four things:

  1. Idempotency (280–287). If the caller supplied a key that matches one of the last 64 transactions, it returns that transaction's version and does nothing. This protects against a network retry applying the same model edit twice.
  2. Runs it (288). The ? returns the error list straight to the caller.
  3. Updates derived state (289). after_transaction keeps the reactive graph and the clip sample in step. That is Parts 5 and 6.
  4. Records history (297–302). It pushes onto the undo stack (trimmed to the 200-entry horizon), clears the redo stack (a new edit invalidates anything you had undone), and appends to the log.

3.7Undo and redo: ordinary transactions

The store keeps three lists (History): past (what undo will reverse), future (what redo will replay), and log (every transaction that ever applied, undo and redo included, bounded by the horizon). The log is what the Bevy bridge reads in Part 4.

Undo pops the last transaction, builds a new transaction from its inverse, labels it "undo: …" with actor System, and runs it through the same run as everything else. Redo re-runs the original ops. Because both go through the normal path, validation, the version bump, the Bevy sync and the model's view of history all work with no special cases. If an undo fails (it shouldn't, but a hand-edited file could make it), the transaction goes back on its stack and nothing changes.

What that looks like over a few keystrokes:

The version only ever goes up, including on undo. That matters for the model: a version number names one exact document state, so “I read version 3” is never ambiguous. The stacked label in the last row is a small quirk: redo pushes the new “redo:” transaction onto past, so undoing it again produces the nested label.

3.8Out to disk: canonical JSON

This is the saved file from the dump example, after the move:

Three decisions shape it:

  • Flat, not nested. Nodes, components and relations are separate tables keyed by id. The file never nests one node inside another. Reparenting changes one "parent" value on one line.
  • Canonical. Keys are sorted, and there is one record per line in a fixed layout. Saving the same document twice gives the same bytes, and a git diff of two saves reads like a list of ops. The sorting comes free from the BTreeMaps (serial.rs:94–97); the one-record-per-line layout is written by hand in save.
  • Tombstones and counters are saved. next_id is in the header, and deleted nodes keep their rows with a "tombstoned" field, so ids stay unique across save and reload.

load trusts nothing. Before it builds a document, it checks the schema version, that every id is below its counter, that every parent exists and admits its child, that there are no parent cycles, that every component is allowed and every required one present, and that every relation points at known nodes. Then it rebuilds the indexes and runs check_invariants:

A bad file becomes an error with a message, before anything else in the app sees it. Part 4 shows that the FFI's document_load runs this validation up front, so a broken file never reaches the running scene.

3.9Out to a reader: views

The file is for machines. A view is for a reader, either a person in the Document panel or the model. The same document, rendered by view.rs:

It's XML-shaped because the tree is the information, and models read XML well. A view is requested with a ViewQuery:

  • Fidelity. skeleton shows types, ids, names and child counts, with no leaf values. summary shows values, but a node with more than 8 children shows only the first 2. full shows everything.
  • Scope and depth render one subtree to a limited depth.
  • Elision is always marked. Any node whose children were left out carries elided and the true count, so a reader can tell “has no children” apart from “children not shown”. Vision doc 04 §6.3 calls this the difference between an empty subtree and an unknown one.

Two rendering details matter later. Attribute names are bare field names (x, w, color) unless two components on the same node share a field name, in which case both are written in full (fill.color, stroke.color); see view.rs:97–109. Every value shown is the resolved value, read through the reactive graph, so a bound leaf shows its current number plus a .bind attribute with the formula. Parts 5 and 6 show both of these, and the <driven-by> element.

Every view starts with <document version="N">. The model sends that number back when it edits, and the edit is refused if the document has moved on since (Part 7).

Before you go on
  • The only way to change the document is Store::apply(TransactionInput), which runs ops on a copy and commits all of them or none.
  • Every op's inverse is computed while it applies. Undo is “apply the inverse as a new transaction”; redo is “apply the ops again”.
  • The version increases by one per transaction, undo included. The log of transactions is the record every other system reads.
  • Data leaves as canonical JSON (for files) or as a view (for readers). Views always mark what they left out.
