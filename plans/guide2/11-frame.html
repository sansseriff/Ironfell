    One frame, in order

    F4 described the bridge as "a sync at the start of the frame and a reconcile pass for gestures". There is more to it now: the engine has a second host (a native macOS app), the boundary is one shared module instead of a wasm-only file, the store has a producer that publishes before the sync, and an ordering bug showed that when a message lands matters as much as what it says. This part follows a frame from the messages that arrive before it to the events that leave after it, system by system, with what each one reads and writes.

    You needF4 (the bridge's queues, sync_document), Part 10 (Drawables, Modes, the spatial scene).
    Filessrc/engine_api.rs, engine_dispatch.rs, host_events.rs, web_ffi.rs, src-ui/worker.ts, src-native/src/{main,bridge}.rs, bevy_app/mod.rs (the schedule), document_bridge/mod.rs, src/lib.rs (WorkerApp::frame).

    11.1Two hosts, one engine

    Commit 9dc4928 added a macOS target in which Tauri owns the window, a CADisplayLink drives Bevy on Metal, and the same Svelte shell runs in a transparent webview on top. To share behaviour, everything the web FFI used to do was moved into engine_api.rs, plain Rust functions over &mut WorkerApp. Each host only decodes its own transport:

    11.2When a message lands

    Every host call does one of three things, and which one matters for ordering:

    KindCallsTakes effect
    Read nowdocument_view, save, selection, inspect, signals, schema, next_ids, placeBetween frames, from the store as it is
    Apply nowdocument_apply (the model's edits, with compare-and-swap on the version), inspect_set (set_through_handle), inspect_scrub (a store gesture), producer freeze, link, import_svgBetween frames, as a real transaction on the store; the next sync finds it in the log
    Queue for a systempointer moves, presses (left_bt_down_at carries its position), tool_key (now including undo and redo), clipboard_paste, document_load (validated now, swapped by the sync)Read by a system in the next frame, in schedule order

    Every call also sets ActivityControl.remaining_frames = 10, which keeps the frame loop running for ten frames (the loop otherwise stops when idle). On the web, pointer moves are buffered by the worker and only the latest is written as a CursorMoved at the start of the next enter_frame. A press lands at its own coordinates, so a press and the first moves of a drag in one slow frame still resolve where the press happened.

    11.3The frame, system by system

    The schedule is declared in bevy_app/mod.rs and document_bridge/mod.rs. Here it is as one table: rows in execution order, columns for the resources that carry state between systems. A filled dot means the system writes that resource, a hollow dot means it only reads it.

    Read down the Store column to see who touches the document. It is written in exactly four places in a frame: the producer's publish, the sync (transactions, gesture commits, undo), the tools (previews and drags), and the session's selection. Two of those, the sync and reconcile_gesture, drain its changes into Drawables and DocumentChanges; prepare_spatial takes its geometry changes. Everything after that only reads.

    Inside sync_document, in order

    1. Skip if no queue has work, the graph has no changes and the version equals SyncedVersion. An idle frame costs one comparison.
    2. Load: a pending document replaces the store, all entities and all draw data go, and every live node counts as affected.
    3. Transactions from PendingTransactions, in order; a rejected one is logged and skipped.
    4. Gesture requests: Commit, CommitMerged (an Alt-drag, Part 13) or Cancel.
    5. History requests: undo, redo.
    6. The log since SyncedVersion, whoever applied it, including the model's synchronous applies from between frames: collect node ids from ops, derived ops and inverses; note whether the tree's shape changed.
    7. Drain the graph's changes: nodes whose resolved values moved, including the producer's publish from the system just before.
    8. If the version moved, push DocumentChanged to HostEvents. Then reconcile the affected set (Part 10's two passes) and, on a structural change, recompute paint order.

    The order of 3–5 is fixed in the code: everything queued as a transaction applies before any queued undo. The next section shows why that ordering had to be fed correctly.

    11.4Three journeys

    A drag frame

    The pointer moved while a selected rect is being dragged. Everything happens within one frame:

    A model edit that arrives mid-drag

    1. Between frames, the worker handles documentCall("apply", …): engine_api::document_apply checks expect_version, then calls Store::apply right away.
    2. The store classifies the edit against the running gesture, sets the gesture's previews aside, applies and solves against the document alone, then either puts the previews back or cancels the gesture with a reason (Part 13).
    3. Next frame, sync_document finds the new transaction in the log and reconciles it.
    4. In PostUpdate, the select tool polls gesture_status for the gesture it owns. If that reads Cancelled, the tool stops: its release will commit nothing, and the model's edit stands.

    Keys in the order they were pressed

    The ordering bug fixed with phase 4: press Delete, then Cmd+Z quickly, and on a slow frame Cmd+Z undid the edit before the delete. The cause was two routes into the frame:

    Rough edge

    The fix restores the order "a transaction, then undo". The reverse within one frame, "undo, then a key that makes a transaction", is still reordered: both reach their queues in the same PostUpdate, and the next sync applies PendingTransactions before HistoryRequests, so the undo would revert the new edit. That follows from sync_document's fixed order. It takes two keys inside one frame, which only a slow frame makes likely.

    11.5After the schedule: render, or don't

    WorkerApp::frame runs the main world's schedule, asks RedrawNeeded (set by decide_redraw in Last) whether anything visible changed, and only then extracts and runs the render sub-app:

    Then the host drains HostEvents (flush_events on the web; the tick loop on native). The shell reacts to documentChanged by re-reading the views it shows; hover and selection events update its own state.

    Before you go on
    • Both hosts call the same engine_api. Inbound document calls are decoded by engine_dispatch's allowlist; outbound events go through HostEvents, drained after each frame.
    • A message is read now, applied now (the model's edits, the inspector), or queued for a system. Undo and redo are queued with the tool keys so they keep their place in key order.
    • In a frame: the producer publishes, then the sync applies transactions, gesture commits and history in that order and reconciles from the log, then the Live set is decided. The tools preview in PostUpdate, reconcile_gesture rewrites draw data the same frame, prepare_spatial updates the scene, and the views rebuild.
    • The render sub-app runs only when something visible changed.
