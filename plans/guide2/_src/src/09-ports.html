Ports, connections and physics

A laser feeds a fiber, which feeds a power meter; a heater warms a block through a thermal link. Entities need a way to be wired together so that a value computed in one flows into another. This part covers roadmap stage F, steps 1–3: port kinds, connections, one-way signals that ride the binding graph, across/through pairs solved as equations, and the two demos (Optics and Thermal) that use them.

9.1The decision: two kinds of variable, one interface

You asked whether ports should carry constraint bundles or bidirectional signals. The answer recorded in ECM §6.1 is both, through one general interface: a port kind declares a bundle of variables, and each variable is one of two sorts.

One-way signal

out → in. Optical power along a fiber. The in-port's value is its partner out-port's value. It compiles to a dataflow edge in the binding graph, evaluated like any binding; cycles are rejected. A back-reflection would be a second signal running the other way.

Across / through pair

Acausal, as in Modelica, Simscape and SPICE. Temperature and heat flow; voltage and current. At a joint the across values are equal and the through values sum to zero. These compile to equations, solved together with each part's own behaviour equations. Loops are fine.

Editing a signal from either end uses the existing handle inversion; it is not another port flow mode. Ports can also have anchors on their pictures. Flexible connections let a follower track its partner; rigid plugging adds a mate constraint for placement. The connection and the mate are separate document objects.

The vocabulary is code, like node types and constraint kinds:

Every port carries signal and pair fields, plus interface metadata; the kind decides which ones mean anything. Storing signal, across and through on every port was step 1 of the plan: the file format holds both variable sorts from the start, so files never need migrating as the solving arrives.

Ports come from definitions

A definition exposes port_spec children and behaviour equations. Input ports define arguments and defaults, output ports hold bindings, and pair terminals participate in the network. Linked entities derive their ports and equations through expansion; detached instances copy them as authored nodes. Templates read those ports, rewritten to the particular entity, so multiple uses show the same live values (Part 2).

9.3Connections

A connection is a connection node under the model root with exactly two connects relations, tagged end: a and end: b. That's all a file stores; nothing about which value flows where.

model entity "laser" (instance of laser) port "out" kind=optical_power dir=out signal = args.power entity "fiber" port "in" kind=optical_power dir=in port "out" kind=optical_power dir=out signal = in.signal · 10^(−loss·length/10) connection domain="optical" connects → laser.out end=a connects → fiber.in end=b

One-way signals are derived bindings

The simple version

Write a binding onto the in-port when the connection is made. Now the file holds the wiring twice (the connection and the binding), deleting the connection must find and remove the binding, and an undo that restores one without the other leaves a ghost.

What was built

Derive the binding from the connection, never store it. Every time the graph is rebuilt, each live, valid one-way connection contributes one binding: in-port's signal reads out-port's signal. Delete the connection and the binding is simply not derived next time.

The reactive graph (Part 3) folds them in alongside the stored bindings, so a signal is evaluated in topological order with everything else, in the same pass:

9.4Across/through pairs as equations

A pair can't be a binding, because nothing says which way it runs: a thermal link relates two temperatures and a heat flow, and which one is "the answer" depends on what's held fixed elsewhere. So pairs become equations, and the solver from Part 4 finds the values.

Assembling the network

network collects every pair port on a live entity. Each port's across and through is an unknown unless it's bound. Ports joined by connections are grouped into nets by union-find (the same trick iron_solve uses for clusters); each net contributes its conservation laws; each live equation on an entity contributes lhs − rhs:

Line 273 skips equations on definitions: a definition's equations describe the template, which has no network of its own. An unconnected terminal ends up in a net of one, where "throughs sum to zero" means it carries no flow, which is the physically right default for an open end.

Solving, and where the answer lives

Every equation becomes a Required term (Part 4's tiers). Linear rows are plain sums; Expr rows evaluate both sides with the unknowns substituted (as quantities with their dimensions, so 2 K/W · 5 W is a temperature) and everything else read from the store. The previous solution (read back from the network's own published signals) is the starting point, so a slider drag converges in a step or two.

The solution is not written to the document. It is published into the reactive graph's runtime layer as producer 1, ProducerId::NETWORK (1313–1320), which readers see beneath bindings. When this part was first written the network had its own physics map; on October 17 it became one producer among several (clips are producer 0, layout is producer 3, host simulations are 3 and up; Part 12):

So the heater's gauge, bound to (#out.port.across − 293.15 K) / 1 K · 6, reads the solved temperature like any value, and when the solution changes, publish invalidates its dependents like any change. resolve_physics runs after every transaction, preview, publish and playhead move (lib.rs:1456). A solved leaf is Locked for editing, because a producer holds it, with the reason "solved by its across/through network; change a source or a parameter instead" (handle.rs:52).

Why not solve-on-apply like constraints?

Constraint solutions (Part 4) are positions: authored state the user owns, so they are written as derived ops and undone with the transaction. Physics solutions are consequences: the temperature is whatever the heater's power and the link's resistance make it. Storing it would put a cache in the file that could disagree with its own inputs. A network that fails to converge keeps its previous solution and reports why through physics_error(); it never rejects a transaction.

So "connect the meter straight to the laser" is something the model can attempt, and if the meter is already fed, it gets back #… already has a connection feeding it and can delete the fiber's connection first.

9.7Anchors, plugging and joints

An empty with an anchor facet locates a port on a picture. Derived anchor.wx, wy and wrot expressions carry its position and facing through ancestor transforms. A following anchor derives its own placement from its connected partner, so the fiber follows the laser when moved. Handle inversion can follow those expressions back to a movable source.

Store::begin_plug, plug_drag and finish_plug preview and commit a connection. Rigid ports also produce a mate constraint; loose ends form a draggable joint. The port and empty tools, mains and link lines make these interfaces authorable on the canvas, rather than available only in demo code.

9.8The electrical schematic is built

The newer Circuit tab uses notation schematic; it is distinct from the optics demo's older Schematic tab. std_parts.xml declares electrical parts as markup. parts.rs turns each into a definition with value input ports, electrical pins, equations and a symbol template. Each pin has an anchored empty in its symbol. The built-in library is read-only; first placement copies the part definition into the document and records import.source = std:<key>.

The notation's context supplies its palette, shortcuts, grid and snapping. The wire tool creates connection nodes and visible paths whose ends bind to anchor coordinates. Joining a wire creates a junction; ordinary geometric crossings do not alone connect nets. Moving or rotating a symbol updates its wire endpoints through the same graph, not by patching path coordinates from the UI.

The existing across/through network solves DC voltage/current values, and bound text labels display live readings. <circuit> is a model macro that returns ops; __iron.netlist('circuit') emits a SPICE-like netlist with solved net voltages. This is the initial DC schematic, not a transient simulator or external SPICE engine.
