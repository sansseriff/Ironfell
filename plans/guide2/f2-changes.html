    Ops, transactions and undo

    F1 ended with a document whose write methods can't be called from outside the crate. This page covers the one door that is open: ops, grouped into transactions. Undo falls out of that design almost for free. The page ends with the two ways data leaves the store: the saved file and the view.

    You needF1: NodeId, Slot, components, LeafPath, tombstones, writes are pub(crate).
    Filesop.rs, lib.rs (Store), serial.rs, view.rs, tests/spine.rs.

    F2.1Why not just set the field?

    The simple version

    Give the document a public setter: doc.set_x(square, 600.0). Everything the project wants from the document then fails:

    • Undo needs the old value, which is gone once overwritten.
    • Bevy needs to know which nodes changed, or it has to rebuild the whole scene.
    • The model sends several changes at once. If the third is invalid, the first two have already happened.
    • History can't say who changed what (a person, the model, the system) or what they meant ("move rect", not "set x14").

    The answer: every change is described as data first (an op), ops are grouped into a labelled transaction, and one applier executes them. Undo, the Bevy sync and the model all read the same log of applied transactions.

    F2.2The nine ops

    #[serde(tag = "t", rename_all = "snake_case")] sets the JSON shape: each op is an object whose "t" names its kind, as in {"t":"set","id":"#2","path":"transform2d.x","slot":200.0}. The model surface builds exactly these objects (F4).

    The central property: every op has an inverse op, and the applier computes it while applying, when the old state is still at hand.

    OpWhat it doesIts inverse
    CreateAdds a node with its components. If the id is a tombstone, restores it.Delete { id }
    DeleteTombstones a node and its live descendants.One Create per tombstoned node, with its placement and components
    ReparentMoves a node under a new parent at a new key.Reparent back
    ReorderChanges only the order key.Reorder to the old key
    SetReplaces one leaf's slot.Set with the old slot
    AddComp / RemoveCompAdds or removes an optional component.The other one
    Link / UnlinkAdds or removes a relation.The other one, with the same relation id

    F2.3Transactions: what goes in, what gets recorded

    Two structs, because the caller and the log need different things. A TransactionInput is what a caller submits: a label, an Actor (Human, Model or System), a timestamp, an optional idempotency key, the ops, and exact (Part 4). A Transaction is what the log keeps: all that, plus the version it produced, the computed inverse, and two things the solver adds in Part 4, derived_ops (what it moved to keep constraints holding) and a solver summary.     F2.4The applier: one function per op

    apply_op takes the working document, the op's index (so errors can say "op 2"), the op, and the version this transaction will produce. It returns the inverse ops or an error. set is the simplest complete arm and the pattern for the rest:

    1. The node must be live (485). live(…)? returns an UnknownNode or Tombstoned error, and ? hands it straight back.
    2. A binding is validated (486–488): every leaf it reads must exist, and it must not end up depending on itself (F3.3).
    3. The node must have the component (489–494). ok_or_else turns "no such component" into an UnknownPath error.
    4. Component::set from F1 type-checks and swaps the value in, returning the old slot (495–497). Line 498 re-checks entities against their definitions (Part 2).
    5. The inverse is built from that old slot (501–505). No other bookkeeping.

    Delete: the one whose inverse needs care

    Deleting a group tombstones it and everything under it. Each node gets its own Create in the inverse, carrying its components, so undo restores the same ids with the same data. The loop walks deepest-first, so the reversed list recreates the group before its children.

    Create, and the rules about ids

    • An id already live is refused (298–300).
    • A fresh id must come from the counter (302–309). Callers reserve ids with Document::next_ids and use them in Create ops; an id below the counter that isn't a tombstone is refused, so ids can't be reused.
    • A tombstoned id means "restore" (301, 318–319). That's how undo of a delete gets the same node back.

    Some checks need the whole transaction in place: a created node's bindings may read a sibling created later in the same transaction (undoing the deletion of a group whose children bind to each other does exactly that). Those are deferred to check_created, run after every op has applied (comment at 333–335).

    F2.5All or nothing: Store::run

    Several ops in one transaction must all apply or none. The simplest correct approach, which is the one used: copy the whole document, apply every op to the copy, and swap it in only if nothing failed.

    The loop doesn't stop at the first error (904–909); it collects every one, because a model fixing a rejected edit wants the whole list in one round trip. The deferred checks follow (910–925). Only if both passes are clean does the copy get the new version and go back to the caller. The comment above run covers the cost: one clone per commit, not per frame, because a drag produces one transaction when it ends (F3.5).

    F2.6Store::apply, the public entry point

    • Idempotency (684–692). A key matching one of the last 64 transactions returns that version and does nothing, so a network retry can't apply a model edit twice.
    • Run and swap (694–696), then after_transaction, which keeps everything derived in step: the reactive graph and clips (F3), constraint clusters (Part 4), the physics network (Part 9).
    • Solve (697–708). post_apply runs the constraint solver over the committed document (Part 4). If the constraints can't hold, the old document is put back and the transaction never happened.
    • Record (717–722): push onto the undo stack (trimmed to 200), clear the redo stack, append to the log.

    F2.7Undo and redo: ordinary transactions

    History keeps three lists: past (what undo will reverse), future (what redo will replay), and log (every transaction that applied, undo and redo included). The log is what the Bevy bridge reads (F4).

    Undo pops the last transaction, builds a new one from its inverse, labels it "undo: …" with actor System, and runs it through the same run as everything else. Redo replays the original ops plus its derived_ops, without solving, so redo reproduces exactly what happened. Because both go through the normal path, validation, the version bump, the Bevy sync and the model's view of history need no special cases.

    ActionVersionpastfutureAppended to the log
    open demo scene1open—v1 "open demo scene"
    drag the square2open, move rect—v2 "move rect"
    Cmd+Z3openmove rectv3 "undo: move rect"
    Cmd+Shift+Z4open, redo: move rect—v4 "redo: move rect"

    The version only goes up, including on undo. A version number names one exact document state, so "I read version 3" is never ambiguous. The model relies on that (F4).

    F2.8Out to disk: canonical JSON

    The saved file from the same example, after the move:

    • Flat, not nested. Nodes, components and relations are separate tables keyed by id. Reparenting changes one "parent" value on one line.
    • Canonical. Keys sorted, one record per line. Saving the same document twice gives the same bytes, and a git diff of two saves reads like a list of ops.
    • Tombstones and counters are saved, so ids stay unique across save and reload. Session-tier nodes (Part 8) are left out.

    load (serial.rs:116) trusts nothing. It checks the schema version (renaming the older spellings from schemas 1 and 2), every id against its counter, every parent and child policy, parent cycles, required components, and relation endpoints, then rebuilds the indexes and runs check_invariants. A bad file is an error with a message before anything else sees it.

    F2.9Out to a reader: views

    The file is for machines. A view is for a reader, a person or the model:

    It's XML-shaped because the tree is the information, and models read XML well. A view is requested with a ViewQuery:

    • Relation picks which structure to walk: the raw tree, the model (entities and their figures, Part 5), or one composition's layout.
    • Fidelity. skeleton shows types, ids, names and child counts; summary shows values but elides long child lists; full shows everything.
    • Elision is always marked. A node whose children were left out carries elided and the true count, so a reader can tell "no children" from "children not shown".

    Attribute names are bare field names (x, w, color) unless two components on one node share a field name, in which case both are written in full (fill.color, stroke.color). Every value shown is the resolved value, read through the reactive graph, so a bound leaf shows its current number plus the formula: h="75" h.bind="#1.slider.value * 300" (F3). Every view starts with <document version="N">; the model sends that number back when it edits (F4).

    F2.10The tests are the specification

    tests/spine.rs is a good summary of what the store promises:

    structural_rulesCycles, tombstoned targets, unknown paths, type rules and child policies are rejected.

    views_mark_elision_and_summary_is_stable_under_hidden_editsEditing a hidden child doesn't change a summary view, which keeps a model's context cache valid.
    idempotency_keys_replay_instead_of_reapplyingA repeated key is a no-op.
    deleting_a_subtree_with_sibling_bindings_undoesThe deferred checks of F2.4: undo restores children that bind to each other.
    Before you go on
    • The only way to change the document is Store::apply(TransactionInput), which runs ops on a copy and commits all or none.
    • Every op's inverse is computed while it applies. Undo applies the inverse as a new transaction; redo replays the ops and any derived ops.
    • The version goes up by one per transaction, undo included. The log of transactions is what every other system reads.
    • Data leaves as canonical JSON (files) or a view (readers). Views show resolved values and always mark what they left out.
