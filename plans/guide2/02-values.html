    Richer values and definitions

    The first guide's document stored numbers, strings, colours and vectors, and every node type was a Rust enum variant. Then the optics demo appeared on the horizon. A laser has a power in milliwatts, a fiber has a loss in dB per km, and a "laser" is not something the Rust code should know about. This part covers roadmap stage B: quantities with units, structured records, fields whose names are only known at run time, and definitions that live in the document as data.

    You needFoundations 1 and 3: components, slots, Value, and the expression language.
    Filesiron_document/src/{units,value,sym,component,definition,serial}.rs, expr.rs's arithmetic, and the demo's bar in document_bridge/demo.rs.

    2.1Quantities: a number that knows its unit

    The simple version

    Store numbers and write the unit in the name. A field called power_mw holds 9.58. It works until someone binds power_mw to a field called power_w, and the laser is a thousand times too bright with no error anywhere. Unit mistakes are silent by construction.

    What was built

    A quantity is an SI magnitude plus a dimension. 9.58 mW is stored as {si: 0.00958, dim: W}. The unit someone typed is presentation only. Arithmetic checks dimensions, so adding watts to kelvin is an error you see the moment you write the binding.

    A dimension is seven small integers: the exponents of metre, kilogram, second, ampere, kelvin, mole and candela. Watts are kg·m²·s⁻³, so their Dim is [2, 1, -3, 0, 0, 0, 0].

    Multiplying two quantities adds their exponents, dividing subtracts them. A result whose exponents are all zero is a plain number again, which is why signal / 1 mW gives a dimensionless ratio you can use as a width in pixels.

    Units come in as text, in files, in expressions, and from the model. parse_unit reads any prefixed or compound unit:

    It splits on the one /, multiplies the atoms on each side, and each atom may carry a prefix (mW, µs) and a power (m2, s^-1). The result is a Unit: a dimension and the factor that turns a magnitude in this unit into SI. So K/W parses to dimension K·kg⁻¹·m⁻²·s³ with factor 1, which matters later: the thermal link's resistance is written 2 K/W in Part 9.

    Going the other way, format picks an engineering prefix so the mantissa reads between 1 and 1000:

    That's what you see in views and in the inspector: 7.94 mW, not 0.00794 W.

    The value enum, now

    Two variants are new since the first guide. Quantity is above. Record is a small structured value with a named schema (a beam with a waist and a wavelength, say). Its fields are read in expressions with dot syntax, #e.params.beam.waist, which parses to Expr::Get. Records exist for the time-domain work in Part 9's future; nothing in the demo uses one yet.

    In files, a quantity is written as {"q": [si, "canonical unit"]}, always in the coherent SI unit, so diffs stay readable. The model surface may also send {"q": "9.58 mW"}, because the model doesn't carry the unit table:

    Arithmetic that checks dimensions

    Addition, subtraction, remainder and comparison need equal dimensions; multiplication and division combine them. A plain number is a quantity with no dimension, so 9.58 mW * 2 is fine and 9.58 mW + 2 is the error cannot combine 9.58 mW + 2. That's exactly the warning you'd have seen in the thermal demo before its port defaults were fixed: cannot combine a plain number - K.

    The lexer turns a number followed by unit characters into a quantity literal, so 640 - x * 300 stays plain numbers while x / 1 mW reads 1 mW as one token (expr.rs:610). The same stage added the floor functions geometry needs (sin, cos, atan2, sqrt, pow, hypot) and the constant pi. The fiber's loss in Part 9 is pow(10, -loss * length / 10).

    Reading the Rust

    fn quantity_op(...) -> Option<Result<Value, EvalError>> has two layers of "maybe". The outer Option says "is this my case at all?": a.as_quantity()? returns None early if either side isn't a number or quantity, and binary then tries vectors and strings. The inner Result says "it is my case; did it work?". same().map(|_| ...) runs the closure only when the dimensions matched.

    2.2Fields named at run time

    Every component so far has compile-time fields: size.w and size.h are written into the Rust by the components! macro, and a LeafPath names a field with a &'static str. A laser's parameters (power) or a fiber's (length_km) are only known from a definition in the document.

    The simple version

    A second kind of field name. Add enum Field { Static(&'static str), Dynamic(String) }. Now LeafPath is no longer Copy, every comparison allocates, and every match on a field name grows a case.

    What was built

    Intern the run-time names. A name seen at run time is leaked once into a &'static str and reused forever after. LeafPath keeps its shape and stays Copy, and files still store plain strings.

    The cost is one small allocation per distinct parameter name for the life of the process, which is nothing. The one component with run-time fields is params, declared in the macro's @dynamic block:

    So a laser entity's power is the leaf params.power, bindable like any other: params.power = {= #slider.slider.value * 1 mW} is how the optics demo connects its slider.

    2.3Definitions are data

    The simple version

    A node type per thing. The demo once had a bar type in the registry. Every new kind of thing (laser, fiber, meter) would need a Rust change, a rebuild and a schema bump, and the model could never invent one.

    What was built

    The registry holds primitives only (rect, circle, path, slider, group, mesh…). A "bar" or a "laser" is a definition node in a library subtree: its parameters, its ports (Part 9), its behaviour equations, and a template per notation saying how to draw it. An entity instantiates a definition.

    Validation

    An entity's parameters must match its definition exactly: same names, each constant of the declared kind, and a quantity of the default's dimension. validate_entity runs at apply time whenever an entity's instance or params change, so the model can't create a laser with a colour parameter it doesn't declare. The error lists what is declared, which gives the model the fix.

    2.4The rename: depiction → figure

    The first plans called a picture of an entity a depiction. It was renamed to figure before it reached the UI: the relation is figures, the definition's template holder is template, and a composition view writes of="#entity". Files written before the rename still load, because the loader renames on read:

    The schema number went to 3 (serial.rs:20), and schemas 1 and 2 still load.

    Rough edge

    A template is evaluated where it sits in the library, so its bindings must make sense at the defaults. A port spec whose signal defaults to the plain number 0, read by a template gauge as signal / 1 mW, is a dimension error, and it was logged every frame until the demo gave port specs defaults in their kind's units (Part 9). Nothing yet checks a template's bindings when the definition is written.
