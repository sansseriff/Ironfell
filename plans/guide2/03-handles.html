    Drags through the store

    In the first guide a drag moved the entity every frame and wrote one op on release. That was enough for a square on its own. It isn't enough once a shadow is bound to the square (the shadow should follow during the drag, not after), or once the dragged value is itself bound (y = 640 − 300·v, where dragging should set v). This part covers roadmap stage A: world transforms inside the store, handles that invert bindings, and previews that reach the screen in the same frame.

    You needFoundations 3 and 4: Store::preview, the gesture overlay, and the reconciler.
    Filesiron_document/src/{geom,handle,lib}.rs, document_bridge/mod.rs (reconcile_gesture, DocumentChanges), bevy_app/mod.rs.

    3.1What the old drag got wrong

    The simple version (the first spine)

    Move the entity now, write the op on release. The square follows the pointer, but its bound shadow reads the document, which hasn't changed yet. So the shadow sits still for the whole drag and jumps on release. A rect whose x is bound can't be dragged at all.

    What was built

    A drag previews values in the store, never entities. Every frame the pointer's position becomes a preview of the right leaf. The reactive graph re-evaluates everything bound to it. A same-frame reconcile pass rewrites the affected entities before Bevy propagates transforms. Nothing in a drag writes a Bevy Transform.

    Three pieces make that work: the store must know where a node is in the world (to turn a pointer position into an x), it must know which leaf a drag should write (the value itself, or a binding's source), and the bridge must apply the preview within the frame.

    Reading the Rust

    chain.iter().rev().fold(Affine2::IDENTITY, |acc, &n| acc.then(local_affine(doc, read, n))) walks the parent chain root first, starting from the identity and composing each node's local transform onto what's accumulated. fold is a loop with an accumulator; |acc, &n| destructures the borrowed id so n is a plain NodeId.

    The decision:

    Read it top to bottom:

    1. A clip-driven leaf (lines 43–45) or one the physics network solved (46–48, Part 9) is locked: its value isn't the user's to set right now.
    2. A constant is Direct. A bound leaf continues, and so does an in-port whose signal a connection derives (51–53, Part 9).
    3. inline substitutes every bound leaf the expression reads by its own expression, recursively, so the result reads only constants. The shadow's x stays #sq.x + 100; a chain like meter reading ← fiber output ← laser output ← laser power collapses to one formula over the laser's power.
    4. The free leaves are the constants the inlined formula reads (58–65). One free leaf and a linear formula gives a Linear handle. Several free leaves, but linear in exactly one, also gives Linear on that one: the fiber's length and loss sit inside an exponent, so dragging the meter's reading moves the laser's power and holds the rest. That rule (72–82) arrived with Part 9.

Each preview also re-solves constraint clusters (Part 4) and the physics network (Part 9), so everything downstream is live while the pointer moves.

    Only drivers are written, meaning leaves a tool previewed on purpose. Leaves the solver moved in response are not written here; the solver reproduces them when the transaction applies (Part 4). A gesture that changed nothing (a click) produces no transaction at all, so a click never shows up in history as a "move".

    3.5The drag API

    Dragging a whole node is more than previewing two numbers: the pointer is in world space, the node's x/y are in its parent's space, the grab point is somewhere inside the node, and the node may be part of a constraint cluster. The store wraps all of that:

    begin_drag decides once, at the grab, which of three modes applies:

    • Cluster (255–265): the node is held by constraints, so the drag places a finger (a target for the grab point) and the solver moves everything (Part 4).
    • Axes: each of x and y has its own handle. A locked axis holds still for the whole drag, with the reason logged once, rather than moving and snapping back.
    • Locked: neither axis can move.

    drag_to in axes mode (293–311) undoes the parent's transform, then the node's own rotation and scale applied to the grab point, to find the origin that puts the grab point under the pointer, and previews that through each free axis's handle.

    Rough edge

    A linear handle needs a single free source. A rect bound to the sum of two sliders is locked, with the reason "bound to 2 free leaves". The roadmap's answer is a constraint cluster (Part 4) or a disambiguation policy (prefer the most recently touched source); neither exists for plain bindings yet.
