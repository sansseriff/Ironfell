Where things stand now

Iron is a document engine with a dock of views. The store owns authored state, bindings, constraints, linked components and layout; Bevy hosts interaction, runtime producers and drawing. This guide follows the code through October 28, 2026, including contexts, schematic wiring, render caches, shared browser/native protocol and native pacing. This part is the map; Parts 2–14 explain the mechanisms.

1.1The same idea, much further

The Foundations' one idea still holds: the document is the truth, and Bevy draws whatever it says. Everything since has been about what the document can say, and how many ways it can be seen. Vision 10 sharpened it on October 17: Iron also computes everything derived from the document (world transforms, solved poses, evaluated bindings), and Bevy is the renderer, the host and the runtime for things that aren't document nodes (Part 10).

1.4One drag, through everything

Move the square whose shadow reads its x. The host sends the press and modifier state through the shared protocol. Picking constructs a hit chain; context rules tell the select tool which node to grab. The tool begins a store gesture and maps the pointer through the view's pan and zoom into document space.

  1. The handle resolves the destination leaf: direct for the square, inverted through a binding for a bound value, locked for a producer-owned value.
  2. The store previews it in the overlay. Bound dependents update, constraints and networks solve, and layouts reflow as needed. Authored state is unchanged.
  3. The post-tool sync_document drains changed values into draw data. The spatial scene updates bounds; touched chunks are re-recorded, while unaffected drawings and tiles are reused. Chrome draws separately.
  4. On release, the same post-tool sync commits one transaction, and the shell receives coalesced state/history events. One undo restores the authored edit. A reply or completed engine frame does not certify display presentation.

Parts 3, 4 and 13 cover the store gesture; Part 7 covers the tools; Part 6 covers the caches; Part 11 places the steps in the actual frame.

1.6Running it yourself

The document, solver, spatial, SVG, text and layout crates test natively. The workspace defaults to wasm, so pass your Mac's target:

cargo test -p iron_document --target aarch64-apple-darwin cargo test -p iron_solve --target aarch64-apple-darwin

The app runs through the /run-iron skill, whose smoke.txt now has a section per stage: drags, the pendulum, Link, embeds, the select tool, the pen, the dock, and the optics and thermal chains. Its expected output is in .claude/skills/run-iron/SKILL.md. Two URL switches are useful when looking at the app: ?layout=default forgets the saved dock layout, and ?bevy=always turns render on demand off.

One known failure: iron_solve's three_link_chain_reaches_a_target hits its 50-iteration cap (Part 4's rough edge).

Before you go on
  • The store still owns everything. It has layers of derived values (overlay, bindings, runtime signals) above the stored constants, none of them saved, and it computes every world transform (Part 10).
  • An edit to a leaf goes through its handle, which may land on a different leaf, through the solver, or nowhere, with a reason.
  • A composition is a diagram, an entity is a thing, and a figure links the two. Views of compositions can nest.
  • Every view renders to its own texture, only when what it shows changed.
