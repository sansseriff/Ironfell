Bindings, the graph and clips

A slider sets a bar's height. A clip turns a torus between one second and four. Neither is a Bevy system: both are data in the document, evaluated by the store. This page covers the expression language, the reactive graph that keeps every binding's value current, the stack of layers a reader sees through, gesture previews, and clips on a timeline. Part 3 builds directly on all of it.

You needF1 (Slot::Bound, Leaf) and F2 (transactions, after_transaction).

F3.1Two simple versions

The simple version A

A Bevy system per relationship: fn bar_follows_slider(…) { bar.h = slider.value * 300 }. The relationship lives in Rust, not in the document: it isn't saved, the model can't see or edit it, undo can't touch it, and every new relationship is new code.

The simple version B

Formula strings, re-evaluated every frame. Saved and visible, but you re-parse text constantly, recompute formulas whose inputs didn't change, and if C reads B, C may run first and briefly show a wrong value (a glitch).

What was built
  • An expression language (expr.rs): formulas stored as a parsed tree, saved and shown as text, reading their inputs through one resolver.
  • A reactive graph (graph.rs): each binding knows which leaves it reads. When one changes, only what depends on it re-evaluates, in dependency order, stopping early when a result didn't change.
  • Layers: gesture previews, clip samples and solved physics sit on top of the stored constants, never written to the document.

F3.2Expressions: a tree, not a string

A bar's top edge, as the demo writes it: 640 - #O.slider.value * 300 (y points down, so a growing bar moves up). Parsed, it's a tree: Bin(Sub, Lit(640), Bin(Mul, Ref(#O.slider.value), Lit(300))). The Ref is its only input.

A literal, a named constant (pi), a reference to a leaf, negation, logical not, a binary operator, cond ? a : b, a function call, and a record field (beam.waist, Part 2). Box<Expr> is how a tree node holds child trees.

Dependencies are read off the tree

deps() walks the tree and collects every Ref. This works because the language can't compute which leaf to read at run time: every reference is written literally. That restriction is deliberate, because it lets the graph be built without evaluating anything. map_refs below it rewrites every reference, which is how a definition's template is copied onto an entity (Part 2).

Evaluation goes through one resolver

Reading the Rust

read: &dyn Fn(Leaf) -> Option<Value> means "any function that takes a Leaf and maybe returns a Value". eval doesn't know where values come from; the caller passes in a lookup. The graph passes one that reads through the layers of F3.4; tests pass canned values.

binary() defines what operators mean: arithmetic on numbers and quantities (dimension-checked, Part 2), +/- on vectors, comparisons, &&/||. Anything else is a type error, never a silent coercion. Text in, text out

Files and views show a binding as text ({"bind": "640 - #O.slider.value * 300"}), so the tree must parse from text and print back to the same text. The parser uses precedence climbing:

Using 1 + 2 * 3: expr(0) reads 1, sees +, and calls expr(prec + 1) for the right side. That inner call reads 2, sees * (higher precedence, so it continues), reads 3, and returns 2 * 3. The outer call builds 1 + (2 * 3). The + 1 on line 846 also makes equal precedences group left: 1 - 2 - 3 is (1 - 2) - 3. The printer mirrors this, adding parentheses only where needed; a test checks that parse then print round-trips.

F3.4The reactive graph

Reactive lives inside the Store and holds everything derived:

Height: the order that avoids glitches

A bound leaf's height is 1 + the largest height among the bound leaves it reads; an unbound leaf counts as 0. Take a diamond: b = a * 2, c = a + b. Then b has height 1 and c height 2. If a changes and dependents run in arbitrary order, c might run first, show anew + bold, then run again. Sorting by height guarantees b runs before c, each once.

Rebuild vs. invalidate

  • Structural transactions (nodes created or deleted, components added or removed, relations linked, a binding set) call rebuild: re-read every bound slot, rebuild edges and heights, re-evaluate everything. It checks the inverse too, because undoing a binding is also structural.
  • Plain value changes (a Set of a constant, by far the most common) call invalidate with just the leaves that were set.

The last three lines keep the other derived state in step: clips, constraint clusters (Part 4), physics (Part 9).

invalidate follows dependents outward to find everything that might need recomputing (dirty), and marks only the direct readers as definitely needing it (primed). Then:

Dirty leaves run in height order (283–284), but only if primed (286–288). When a result differs from the old one (302), its dependents become primed. When it's the same, they don't, and propagation stops there: the equality cutoff. A threshold binding w > 100 ? 1 : 0 re-evaluates when w goes from 150 to 160, still gives 1, and nothing reading it runs.

F3.5Gestures: preview every frame, commit once

The simple version

Scrubbing the slider submits a Set every frame. The bar follows, but a two-second scrub fills history with 120 "set slider" entries, and undo steps back one frame at a time.

What was built

The overlay. Store::preview puts a value on top of the document for one leaf, and dependents re-evaluate at once. commit_gesture turns the previews into one transaction; cancel_gesture drops them.

The store's preview also re-solves any constraint clusters and the physics network (Parts 4 and 9), so everything downstream of a dragged value moves in the same frame. Commit:

It writes a Set for each leaf the gesture drove (420: not leaves the solver moved for it, which solve-on-apply reproduces), skipping bound leaves (426: a derived value has no handle here) and values equal to the document. If nothing qualifies, it cancels and records nothing.

The slider is the simplest gesture. While it's dragged, the pointer becomes a value in the slider's own space and is previewed; nothing else is sent anywhere:

On release the bridge commits it as "set slider" (F4). Part 3 generalises this: previewing a value for a leaf through its handle (preview_target), so dragging a bound bar sets the slider it's bound to.

F3.6Clips on a timeline

The simple version

Keyframes on the property, or Bevy's animation system. Either the animation isn't a thing you can select and retime, or it lives outside the document where nothing can see it.

What was built

A clip is a node; its target is a relation; sampling produces a layer. A clip (child of a timeline) has Timing and Clip components and an animates relation to each target. The sample at the playhead is the graph's animated layer.

prop is a leaf path as a string ("transform3d.rot"). from and to are Any, because their kind is the target's: a Vec3 for a rotation, a Number for an x. Nothing names the target; the animates relation does.

For every clip and every animates relation leaving it (95): apply the relation's optional offset, and skip the target before the clip starts (99–103), so it shows its authored value. Progress u is capped at 1 (104), so after the end it holds to. Conflicts are reported, not resolved: a missing leaf, a bound target (111–114), or endpoints of the wrong kind put an error under the clip's id, and the timeline draws that clip red. Then ease, interpolate, record (131–133).

The playhead lives in the store, but isn't saved

The playhead is editor state, like a scroll position: a field on Store, not part of the Document, so it's never saved or undone. set_time resamples, and set_animated compares the new sample with the old, reports the leaves that moved, and invalidates their dependents, so a binding that reads an animated leaf follows the animation. The timeline panel pushes the time to the store before each document sync (timeline.rs:21).

"Why is this moving?"

Because a target is a relation, the answer is one lookup, relations_to, and views render it on the driven node as <driven-by ref="#6" rel="animates" prop="transform2d.x"/>. Bindings show as .bind attributes; relations that drive a node (clips, and later constraints) show as <driven-by>. A clip-driven leaf has no handle while the clip drives it: dragging it is refused with the reason, rather than silently writing a constant the clip would hide (Part 3).

Rough edge

Two clips on one leaf: the higher-numbered clip silently wins where they overlap (out.values.insert on line 132). Clip-against-binding conflicts are reported; clip-against-clip ones aren't.

Before you go on
  • A binding is an Expr tree with static dependencies, saved as canonical text and validated at apply time for dangling reads and cycles.
  • The graph evaluates in height order (no glitches) with an equality cutoff (no wasted work); it rebuilds on structural changes and invalidates on value changes.
  • Every read goes through the layers: overlay → binding → physics → clip → constant. Only the last is stored.
  • A gesture is a string of previews and one commit. A clip is a node, its target a relation, its effect a layer.
