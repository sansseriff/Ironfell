Why the worker's Vello frame was late, and how to keep it on time

Chrome on macOS, 60 Hz, a light page (the Latency view alone). Times are in ms, measured from Chrome traces (plans/rendering/latency-view.md §7). One drag event is followed from the OS to the screen. Arrows show what triggers what. The DOM trackers set the bar: Vello should appear on screen at the same vsync they do.

1. Before: the worker ticks at rAF measured

Vello ≈50–52 ms against the DOM's ≈36 ms: one frame late. The tick was ready after the draw in 192 of 192 frames.

  1. The browser delivers one coalesced drag event per frame, about 12.4 ms in. The page's pointerrawupdate posts it to the worker, which only stores it.
  2. At vsync 1 the DOM trackers draw (pointermove). The page's light frame is committed by ~17.6 ms.
  3. The compositor draws as soon as the page's frame is ready (~17.9 ms). It does not wait for the worker's canvas, which is a separate surface.
  4. The worker's rAF starts its tick only at vsync 1. Its frame is sent at ~21.5 ms, too late for that draw, so the draw after vsync 2 picks it up.

It was on time in the full layout by accident: the Document view's forced layout made the page's frame slow (~5 ms), so the draw waited until after the worker's frame.

2. The fix: tick when the motion arrives measured

Vello ≈36 ms, the same vsync as the DOM, in every layout in Chrome and Safari. Ready before the draw in 190 of 190 frames. Built: BrowserRuntime.tickOnInput.

  1. The pointer message starts the tick at once (~12.7 ms), at most once per frame.
  2. The tick (~4 ms) finishes before vsync 1. The worker's next BeginFrame sends the frame (~16.9 ms).
  3. At vsync 1 the worker's rAF skips its tick: the motion has already been rendered.
  4. The compositor's draw at ~17.9 ms already has the new Vello frame, as well as the new DOM.

The budget runs from the motion's arrival to the draw: ≈5.2 ms, of which the tick uses ≈4 ms. A longer tick (dashed) misses the draw and is one frame late, the same as before the fix, never worse.

3. Proposal: hold the page's frame for the worker not built

Needs cross-origin isolation (COOP + COEP headers) for SharedArrayBuffer. Shown with a heavier, 8.3 ms tick that the fix alone would miss.

  1. When the pointer message starts a tick, the worker sets a shared flag to pending (Atomics.store).
  2. At vsync 1 the DOM trackers draw as usual. Then the page's rAF reads the flag. While it is pending, it spins on Atomics.load; the main thread can't use Atomics.wait. The spin stops at a cap.
  3. The worker finishes, its BeginFrame sends the frame, and it sets the flag to done.
  4. The page's rAF returns and its frame commits. The compositor, which waits for the page, draws with both new.
  5. If the tick finished before vsync (the normal case), the flag is already done and nothing is held.

The cap matters. A fixed hold of 6 ms past vsync kept everything on time (?latencyBusy=6); 9 ms made Chrome draw without the page, putting the whole page, DOM included, a frame late. The limit is somewhere in that shaded band, and Safari's is unmeasured. The budget grows from ≈5 ms to roughly 10–11 ms. While the main thread holds, it handles no input; the DOM still lands in the same vsync.
